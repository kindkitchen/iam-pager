# User authentication

## Outcome

Introduce an interface-first session and authentication foundation before adding
authenticated product behavior:

- every request reaching application routing has a new server-generated request
  ID and a resolved session;
- a browser without a valid credential receives a guest session rather than an
  unauthenticated null state;
- the first session transport is a secure cookie strategy, independent from
  session storage;
- successful authentication upgrades the logical guest session, saves the
  external user identity, and rotates the bearer credential;
- authentication orchestration supports several concurrently registered
  strategies;
- the first strategy is Google OAuth, integrated through
  `jsr:@kindkitchen/gauth@0.4.1`;
- development and tests use gauth's local preset and mocked Google consent
  screen before real Google credentials are required.

The session/authentication implementation, integration tests, and working local
flow are the required milestone. Header and authenticated navigation work is
explicitly gated behind it and must not reshape the core contracts.

## Non-negotiable design decisions

1. **Separate request, session, authentication, and UI concerns.** Fresh routes
   and components consume typed application interfaces; they do not own session
   or OAuth logic.
2. **Separate transport from storage.** `CookieSessionStrategy` only reads,
   writes, and expires an opaque credential. A `SessionRepository` owns session
   records. Do not serialize identity, OAuth state, profile data, or provider
   tokens into the cookie.
3. **Use a stable logical session and a rotatable credential.** Preserve the
   logical session ID while upgrading guest to authenticated so guest activity
   remains attributable, but rotate the cookie credential atomically after
   authentication. Store only a hash of the credential server-side; the
   pre-upgrade credential must stop resolving.
4. **Use discriminated session state.** A request always receives either a
   `guest` or `authenticated` session, never `undefined`. Authenticated state
   references a saved application user/external identity.
5. **Keep provider identity stable.** Uniqueness is
   `(strategy_id, provider_subject)`, using Google's verified `user_info.id`,
   never email. Do not auto-link identities from different strategies by
   matching email.
6. **Keep OAuth secrets and tokens server-side.** The session stores no Google
   access, ID, or refresh token. Discard them after verified identity extraction
   unless a future encrypted credential-store interface has a concrete use.
7. **The application owns OAuth state validation.** gauth documents `state` as
   opaque and does not verify it. Store a hash of each state plus its PKCE
   `code_verifier`, strategy, safe return path, creation time, and one-use
   status against the guest session. Expire attempts after 10 minutes and cap
   pending attempts per session (for example, five) so multiple tabs work
   without unbounded storage.
8. **Authentication must not weaken direct-content isolation.** Session
   middleware may add headers/cookies to direct responses, but must not add the
   site shell, change the body or declared length, expose credentials to page
   content, or relax the existing CSP sandbox.
9. **Initial repositories may be in-memory behind interfaces.** Document
   process-restart and multi-instance limitations. Cookie transport is not a
   substitute for durable/shared session and identity storage.
10. **Reserve the route namespace.** Add `auth` to `forbidden_namespaces`;
    authentication routes must never collide with direct page locators.

## Proposed domain contracts

Names may be refined, but retain these boundaries and behaviors.

### Request context

Define a typed Fresh state instead of `Record<string, never>`:

```ts
interface AppRequestContext {
  request_id: string;
  session: Session;
}

interface State {
  request_context: AppRequestContext;
}
```

Generate a fresh, server-owned request ID for every routed request. Do not trust
an inbound `x-request-id` as the canonical value. Return the ID as
`x-request-id` for diagnostics; do not expose the internal session ID as a
response header.

### Session model and services

Use interfaces such as:

- `SessionTransport` — extract a credential from a request and attach/expire it
  on a response;
- `SessionRepository` — resolve by credential hash, create a guest session, save
  bounded OAuth attempts, atomically consume an attempt, upgrade a session,
  rotate a credential, revoke, and expire records;
- `SessionService` — the only orchestration surface used by
  middleware/authentication;
- `Clock`, `IdGenerator`, and `CredentialGenerator` — injectable dependencies
  for deterministic tests;
- `MemorySessionRepository` — first process-local implementation;
- `CookieSessionStrategy` — first transport implementation.

A session record needs at least a stable session ID, `guest | authenticated`
kind, creation/last-seen/absolute-expiry timestamps, current credential hash,
revocation state, bounded pending authentication attempts, and authenticated
user reference when upgraded. Expired, revoked, missing, or malformed
credentials resolve to a newly created guest session.

Use cryptographically random credentials with at least 256 bits of entropy and
hash them before repository lookup/storage. Avoid refreshing the cookie and
repository timestamp on every request; use a tested renewal threshold to limit
write amplification.

Centralize configurable defaults and test them with a fake clock:

- guest session absolute lifetime: 7 days;
- authenticated idle lifetime: 30 days, with a separately configurable absolute
  lifetime;
- OAuth attempt lifetime: 10 minutes.

### Identity and authentication

Use interfaces such as:

- `IdentityRepository` — atomically find-or-create an application user/external
  identity by `(strategy_id, provider_subject)` and update non-authoritative
  profile fields;
- `AuthenticationStrategy` — stable strategy ID plus provider-neutral `begin`
  and `complete` operations;
- `AuthenticationStrategyRegistry` — accepts several implementations, rejects
  duplicate IDs, and resolves one without conditionals in routes;
- `AuthenticationService` — starts attempts, validates/consumes callbacks, saves
  identity, and asks `SessionService` to upgrade;
- `MemoryIdentityRepository` — first process-local implementation.

The external identity should retain application user ID, strategy ID (`google`
initially), provider subject, email, optional display name/picture, and
created/updated timestamps. Treat email/name/picture as profile attributes, not
proof of identity. Unknown strategies are a clear `404`; duplicate registration
fails at composition time.

## Implementation phases

### Phase 1 — Session foundation

1. Add `lib/session/` model, interfaces, memory repository, service, cookie
   strategy, and focused exports. Keep raw HTTP cookie handling in the strategy.
2. Use a host-only cookie. Production defaults: `__Host-iam_pager_session`,
   `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`. Provide an
   explicit non-secure localhost cookie name/config for development; never
   silently disable `Secure` in production.
3. A malformed, attacker-chosen, expired, revoked, or unknown cookie must
   produce a new guest session and replacement cookie, not an error or a session
   with attacker-controlled identity.
4. Add root Fresh middleware that resolves/creates the session before the route,
   stores `AppRequestContext`, calls the route exactly once, and applies pending
   `Set-Cookie` plus `x-request-id` to success, redirect, error, API, and
   direct-content responses.
5. Update `utils.ts` typing and composition in `lib/app.ts`. Add `auth` to
   forbidden namespaces.
6. Keep generated/static build assets out of the semantic guarantee if Fresh
   serves them before application routing; document the exact boundary as “every
   request reaching app routing.” Site, API, auth, missing-route, and
   direct-content requests are mandatory.

Tests:

- missing cookie creates one guest session and a valid cookie;
- valid cookie resolves the same logical session on subsequent requests;
- malformed/unknown/expired/revoked credentials create a replacement guest;
- credential hashes, not plaintext credentials, are stored;
- cookie attributes differ only by explicit local/production configuration;
- every routed response gets a unique request ID and typed session state;
- middleware preserves status, body, `Content-Length`, existing headers, and
  direct-content CSP;
- concurrent first requests and renewal behavior do not create inconsistent
  repository state;
- `auth` is rejected as a publishing namespace.

### Phase 2 — Multi-strategy authentication core

1. Add `lib/auth/` interfaces, models, registry, authentication service,
   in-memory identity repository, and fake strategies for tests.
2. Implement provider-neutral routes/adapters for:
   - `GET /auth/:strategy/start` — create a bounded, expiring attempt and return
     `303` to the strategy authorization URL;
   - `GET /auth/:strategy/callback` — require `code` and `state`, atomically
     consume the matching attempt, complete provider authentication, save
     identity, upgrade the session, rotate the credential, and redirect to a
     validated local return path;
   - `POST /auth/logout` — revoke/clear authenticated credentials and
     immediately establish a fresh guest session because requests never have a
     null session.
3. Allow only same-origin relative `return_to` paths beginning with `/`; reject
   protocol-relative and encoded external redirects. Default to `/`.
4. Use a session-bound CSRF token for logout. Never implement logout as `GET`.
5. Bound callback query values and return generic browser-safe failures. Log
   only request ID, strategy ID, and an internal error category; never log
   cookies, OAuth code/verifier/state, tokens, or raw gauth causes.

Tests:

- two fake strategies can be registered and selected independently;
- duplicate IDs fail at startup and an unknown ID returns `404`;
- start stores a hashed state and verifier tied to the current guest session;
- missing, mismatched, expired, cross-session, and replayed state all fail
  without upgrading;
- a provider failure consumes or invalidates the attempt safely and leaves a
  guest session;
- success find-or-creates by provider subject, upgrades the logical session,
  rotates the credential, and makes the old credential unusable;
- same provider subject signs into the same application user even if email
  changes;
- equal email from another strategy is not auto-linked;
- logout requires valid CSRF, revokes authenticated access, rotates credentials,
  and returns a guest session;
- unsafe return paths cannot create an open redirect.

### Phase 3 — Google strategy through gauth 0.4.1

1. Add an import-map entry pinned to `jsr:@kindkitchen/gauth@0.4.1`; let
   `deno.lock` record its graph. Add the compatible direct Effect import
   required to construct/provide its layers (`npm:effect@^4.0.0-beta.91`)
   because this repository uses manual `node_modules`, then verify a clean
   dependency install/check. Do not deep-import package internals.
2. Implement a thin `GoogleGAuthStrategy` adapter around the package's exported
   `GAuth.Interface`:
   - call `generate_sign_in_url` with `scope: ["openid", "email", "profile"]`,
     application-owned state, and the exact callback URI;
   - save returned `ctx.code_verifier` only in the server-side attempt;
   - call `process_callback_payload` with callback code and verifier;
   - map verified `user_info.id/email/name/picture` to the application identity
     result;
   - map gauth 0.4.1 `GAuthErr` to an internal provider failure without leaking
     its cause.
3. Select presets only in the composition root/configuration:
   - local/test: `await GAuth.load_preset.local()`, provide its `Requirements`
     layer with callback and mock-consent URLs, then provide `Preset`;
   - real Google: `await GAuth.load_preset.original()`, provide client ID,
     client secret, and allowed redirect URIs to its `Requirements`, then
     provide `Preset`.
4. Validate configuration at startup. Local mode needs no Google secrets. Real
   mode must fail closed when credentials, HTTPS callback origin, or allowed
   redirect URI are missing/invalid.
5. Keep the strategy registry capable of containing Google and additional
   strategy implementations simultaneously; environment selection changes
   Google's implementation preset, not the registry abstraction.

Tests:

- adapter passes exact scope/state/callback inputs to an interface fake;
- adapter maps verified profile fields and `GAuthErr` correctly;
- local and original composition choose the intended preset from explicit
  config;
- no live Google network call or real secret is needed in automated tests;
- `deno task check`, `deno task test`, and `deno task build` resolve the pinned
  package graph under manual `node_modules`.

### Phase 4 — Mocked consent screen and working local flow

1. Add a development-only mock-consent route under `/auth/google/` that renders
   `local.Requirements.render_consent_screen(...)` from gauth. Feed it the
   generated state and redirect URI. Do not copy or reimplement the package's
   mock HTML.
2. The route must be unreachable (`404`) unless local auth mode is explicitly
   active. Apply `no-store`, `frame-ancestors 'none'`, and an intentional HTML
   content type.
3. Exercise the real browser flow locally: guest request → Google start →
   package mock consent → callback → identity save/session upgrade/credential
   rotation → authenticated request → logout → fresh guest.
4. Add an integration test over the same route handlers using a cookie jar and
   parsed redirects. Assert the mocked form posts the package-generated JSON
   code/state back through the application callback.
5. Ensure callback errors remain recoverable: show a small site-owned failure
   response with a retry link, retain no reusable attempt, and do not destroy
   unrelated session state.

### Phase 5 — Core gate and documentation

The lower-priority UI phase is blocked until all items below pass:

- every routed request has request ID plus guest/authenticated session state;
- cookie transport, memory repositories, strategy registry, Google local preset,
  callback validation, upgrade, rotation, and logout are covered by tests;
- the mocked consent flow works manually without Google credentials;
- the existing guest publishing and direct-delivery tests remain unchanged in
  behavior;
- `deno task check`, `deno task test`, and `deno task build` pass;
- README documents local sign-in and real-Google environment variables;
- `docs/` records session/cookie boundaries, identity uniqueness, OAuth state
  ownership, strategy registration, storage limitations, and security
  assumptions;
- specification updates settle `OQ-AUTH` for this first flow and align
  `CP-NAMESPACE`/`QT-AUTHORITY`;
- CHANGELOG records the implementation and test count.

## Lower-priority targets — only after the core gate

These must consume `AppRequestContext` and authentication interfaces without
changing their contracts.

### Thin authentication header

- Add a thin site-only header; never add it to direct page responses.
- Guest state shows a concise Google sign-in invitation targeting the generic
  strategy start route.
- Authenticated state shows the saved display name or email, optional provider
  picture with safe fallback, and an accessible account-menu trigger.
- Server-render the initial state so the page does not flash from guest to
  authenticated. Do not expose provider tokens or raw session identifiers to
  Preact.

### Authenticated navigation

- Present compact links for profile, settings, and logout; collapse them into an
  accessible hamburger/account menu at narrow widths.
- Use semantic navigation, keyboard operation, visible focus,
  `aria-expanded`/`aria-controls`, Escape/outside-click behavior where scripting
  is used, and no hover-only controls.
- Logout is a CSRF-protected `POST` form, not a link that mutates state with
  `GET`.
- Do not ship broken profile/settings links: add explicit site-owned placeholder
  routes or defer individual links until their routes exist.
- Add component/state tests and responsive browser smoke coverage for guest,
  authenticated, keyboard, and narrow/wide states.

## Completion criteria

The required task is complete when phases 1–5 pass and are documented. The UI
targets may then be implemented or split into a follow-up task without delaying
the verified session/authentication foundation.

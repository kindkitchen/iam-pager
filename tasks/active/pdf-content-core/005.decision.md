# Bound the first PDF content contract

The first PDF core accepts at most 16 MiB and requires a byte-zero PDF 1.0–1.7
or 2.0 header. Lightweight terminal validation requires the final
`startxref`/`%%EOF` structure to target either a classic xref table or an
indirect `/Type /XRef` stream object. This catches obvious non-PDF and truncated
inputs but is explicitly not sanitization, exploit detection, or malware
certification.

A suggested filename is required, bounded to 255 UTF-8 bytes, and must satisfy a
portable path/control/reserved-name policy. Its suffix never establishes media
type: delivery is always `application/pdf`. The handler declares both `inline`
and `attachment`; the resolved generic endpoint selects between them. HTTP byte
ranges and upload buffering are deferred to `pdf-content-http` under this bounded
core limit.

# Namespace reservation and publishing authorization

Both completed foundations converge here: `user-authentication` closed with
"Next: persistent namespace ownership and authenticated publishing
authorization", and `content-publishing` deferred "authenticated namespace
reservation". This task is the DS-PROTECT core that connects them.

## Goal

An authenticated creator can reserve a unique namespace. Reservation prevents
guest and cross-user replacement of pages in that namespace. Publishing checks
ownership; everything else (delivery, guest publishing into unreserved
namespaces) keeps its current behavior.

## Spec anchors

- `DA-NAMESPACE` — reservation semantics, guest overwrite rules, consistent
  validation between publishing and lookup.
- `DA-LOCATOR` — case-insensitive uniqueness, publisher casing preserved.
- `CP-NAMESPACE` — required creator abilities; currently marked "not
  implemented yet".
- `DS-PROTECT` — the delivery slice this task starts.
- `OQ-AUTH` — reservation is an authorization capability, not an effect of
  authentication.

## Authorization rules (business core)

| Namespace state     | Guest publish            | Owner publish | Other authenticated user |
| ------------------- | ------------------------ | ------------- | ------------------------ |
| unreserved          | allowed (may be replaced)| allowed       | allowed                  |
| reserved            | rejected                 | allowed       | rejected                 |

Reserving a namespace does not delete or transfer existing guest pages in it;
it stops further non-owner writes. Delivery of public content is unaffected.

## Scope

In:

- namespace domain model, repository interface, in-memory implementation;
- concurrency-safe, case-insensitive reservation with preserved casing;
- reservation use-case service bound to the authenticated user;
- publishing authorization wired into the existing publish path;
- API and site surfaces for reserve/list and rejection feedback;
- spec, README, CHANGELOG reconciliation.

Out (explicit follow-ups):

- durable persistence — queued `durable-storage` task;
- page management (update, delete, public/private, rename) — rest of
  DS-PROTECT / CP-MANAGE;
- multiple additional namespaces per account beyond a working list shape;
- namespace release/transfer policy.

## Constraints

- Interface-first: services depend on `interfaces.ts` contracts, matching the
  existing `lib/*` layout (model / interfaces / service / memory-repository).
- Logic lives in raw code; HTTP and UI are thin representations over the same
  use-case layer (same rules for site and API, `OQ-API`).
- Namespace validation reuses the locator engine rules so publishing and
  reservation can never diverge (`DA-NAMESPACE`).
- The atomicity contract of reserve must be stated on the interface so future
  durable implementations can satisfy it (feeds `durable-storage`).

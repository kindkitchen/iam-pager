# Sub-task plan S1-S7

Ordered, individually understandable portions. Each has a "done when" gate.
S1-S4 are the business logic; S5-S6 are representations; S7 closes the loop.
If implementation diverges from this plan, record a `decision` entry and amend
the plan's assumptions in `SKILL.md`; if it diverges from the specification,
amend the specification in the same change set.

## S1 — Namespace domain model and interfaces

`lib/namespace/`: `model.ts` + `interfaces.ts`.

- `NamespaceReservation`: namespace (as supplied), owner user id, reserved_at.
- `NamespaceRepository` contract:
  - `reserve` — atomic check-and-reserve; exactly one winner under concurrent
    attempts for the same case-insensitive name; losers get a typed `taken`
    outcome, not an exception;
  - lookup by namespace (case-insensitive), list by owner.
- Contract text states: case-insensitive uniqueness, supplied casing preserved
  in stored/returned values, atomicity requirement (`DA-LOCATOR`,
  `DA-NAMESPACE`).
- Read-side view used by publishing (ownership lookup) is part of the
  interface, so the publish path never needs the full repository.

Done when: interfaces compile, contracts documented, no implementation yet.

## S2 — In-memory repository plus reusable contract test suite

- Memory implementation of `NamespaceRepository` (same pattern as
  `lib/content/memory-repository.ts`).
- A shared, implementation-agnostic conformance test suite exercising the
  contract: reserve, duplicate rejection across casings, casing preservation,
  owner listing, concurrent reserve of the same name yields one winner.
- The suite is written to run against any future implementation — this is the
  seam the queued `durable-storage` task plugs into.

Done when: memory implementation passes the conformance suite.

## S3 — Reservation use-case service

`lib/namespace/service.ts` implementing the reservation interfaces.

- Reserve: requires an authenticated user (identity from the session
  foundations of `user-authentication`); validates the namespace through the
  locator engine so publishing and reservation share one rule set; typed
  outcomes: `reserved`, `invalid`, `taken`, `unauthenticated`.
- List own reservations for the account view (`CP-NAMESPACE`).
- No HTTP concepts in this layer.

Done when: service tests cover all outcomes including double-reserve by the
same user and reserve of a namespace already containing guest pages.

## S4 — Publishing authorization (core integration)

Wire ownership into the publish path without spreading it around.

- An authorization policy behind an interface, consulted by the publishing
  use-case: input namespace + acting identity (guest or user id), output
  allow/deny per the rules table in [[001.draft]].
- `PublishingService` (or a thin authorizing wrapper implementing
  `PagePublisher`) rejects with a distinct typed authorization outcome —
  publishing must not conflate `invalid`, `too-large`, and `forbidden`.
- Guest overwrite semantics in unreserved namespaces stay exactly as shipped
  by `content-publishing`; delivery path untouched.

Done when: use-case tests prove the full rules table, including
reserve-then-guest-publish rejection and owner overwrite of pre-reservation
guest content in the same namespace.

## S5 — HTTP API surface

- `POST /api/namespaces` — reserve; maps typed outcomes to statuses
  (created / conflict / unprocessable / unauthenticated).
- `GET /api/namespaces` — reservations of the current authenticated session.
- `POST /api/pages` gains the authorization rejection with a stable error
  shape distinguishable from validation errors.
- Same use-case layer as the site; routing choices stay collision-safe
  (`OQ-ROUTES`).

Done when: HTTP tests cover the new endpoints and the publish rejection, and
the API error contract is documented alongside existing API docs.

## S6 — Site UI

- Authenticated profile-oriented area: reserve form and own-namespace list
  (first visible piece of the "manage" product direction).
- Guest publish form surfaces the reserved-namespace rejection clearly instead
  of a generic failure.
- Components in CamelCase; no business rules in components — presentation over
  S3/S4 outcomes only.

Done when: a signed-in user can reserve and see namespaces in the browser; a
guest attempting a reserved namespace gets an understandable refusal.

## S7 — Spec reconciliation, docs, and acceptance

- Update `capabilities.md` (`CP-NAMESPACE` "not implemented yet" line),

- Record any divergence between this plan and what was actually built as a

- Full gates: `deno check`, tests, production build smoke as in prior tasks.

Done when: docs match behavior, all gates pass, task summary entry written.

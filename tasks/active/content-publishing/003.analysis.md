# Locator engine and content CRUD interface design

Scope of this step: the routing-agnostic domain layer under `lib/` — locator
model, strategy interface, engine, first strategy (`path-slug`), and the content
CRUD interfaces. No HTTP routing, no `MdPage` implementation, no storage
implementation yet.

## Placement

New top-level `lib/` directory (`lib/locator/`, `lib/content/`), separate from
`routes/`. Per `QT-BOUNDARIES`, locator operations must not assume a path,
subdomain, or other public URL mapping; keeping the layer out of the Fresh route
tree makes that boundary physical, and both the site and the API (`CP-PUBLISH`:
same rules through site and API) import the same module.

## Locator model (`lib/locator/model.ts`)

- `Locator = { namespace, page_name? }` — direct transcript of `DA-LOCATOR`.
  Absent `page_name` addresses the namespace's default page. A page name may
  span many slugs; it is stored joined with `/`.
- `locator_key(locator)` returns the lowercased identity key. `DA-LOCATOR`
  demands case-insensitive uniqueness with publisher casing preserved, so
  identity is a derived key and the `Locator` fields keep original spelling. The
  key doubles as the `ContentRepository` key.
- Resolution outcome is a discriminated union
  (`ok | not_a_locator | invalid_segment | forbidden_namespace`), not an
  exception. `CP-DELIVERY` requires distinguishing invalid, missing, private,
  and unavailable outcomes; unions force callers to branch, and "path is the
  site root" is normal control flow, not an error.

## Strategy vs engine split

- **Strategy** (`LocatorStrategy`) is a pure bidirectional mapping:
  `resolve(pathname) -> LocatorResolution` and `format(locator) -> pathname`.
  `format` exists because `CP-PUBLISH` must return a direct URL, and a
  bidirectional contract is testable as a roundtrip property.
- **Engine** (`LocatorEngine`) owns policy: strategy registry, default strategy
  selection, and the forbidden-namespace list (`site` at minimum; the draft says
  the list may grow). Forbidden namespaces are a routing- conflict policy
  (`QT-ROUTING`: page routes must not consume site, management, API, or asset
  routes) that must hold for every strategy — so a new strategy cannot
  accidentally re-allow `site`. Matching is case-insensitive.
- The engine takes strategies via constructor options. Rejected alternatives:
  - _global registry with side-effect registration_ — hidden wiring, untestable
    order dependence;
  - _engine iterating all strategies until one matches_ — a deployment picks one
    URL mapping (`DA-LOCATOR`); ambiguity between mappings has no product
    meaning. Explicit `strategy_name` selection is available where needed.

## First strategy: `path-slug`

First path slug is the namespace; everything after it — even across many slugs —
is the page name. Segment handling for the MVP:

- split on `/`, drop empty segments (tolerates trailing and doubled slashes);
- percent-decode each segment; decode failure → `invalid_segment`;
- reject `.` and `..` and any decoded segment containing `/` (path and
  encoded-slash smuggling) → `invalid_segment`;
- empty path → `not_a_locator` (the root belongs to the site, `QT-ROUTING`:
  invalid/missing must not masquerade as the home page — and vice versa).

Charset tightening (allowed characters, length limits) is left open; the spec
(`DA-NAMESPACE`) only requires validation to be consistent between publishing
and lookup, which it is because both go through the same strategy.

## Content CRUD interfaces (`lib/content/`)

Interface-first per the draft: a content type becomes usable by satisfying
`ContentTypeHandler<Input, Data>`:

- `validate(unknown) -> ContentResult<Input>` — narrow untrusted input;
- `derive(Input) -> Data` — publish-time derivation (e.g. `md -> html`), so
  derived representations are stored once, not rebuilt per request;
- `render(Data) -> DeliveryPayload` — delivery-time raw payload (body + media
  type + optional download filename, `DA-CONTENT`).

`ContentRepository` is CRUD keyed by `locator_key`:

- `get`, `put`, `delete`; `put` is create-or-replace because the guest flow
  always places content at a location and has no separate update (`001.draft`).
  Namespace protection (`DA-LIFECYCLE`) is enforced above the repository, which
  stays a dumb store — content bindings must not assume one storage
  implementation (`QT-BOUNDARIES`).

`ContentRecord` carries `content_type` (discriminator to its handler), the
type-specific `data`, `ContentMeta` (media type, size, download filename), and
timestamps.

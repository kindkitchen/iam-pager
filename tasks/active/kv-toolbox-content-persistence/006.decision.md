# Route all KV access through one project-owned gateway

All application persistence interaction with Deno KV will pass through a narrow
project interface whose production implementation owns `KvToolbox`. Repository
implementations depend on that interface; they do not receive or expose the
concrete wrapper.

The implementation delegates ordinary record and blob operations to
kv-toolbox. Its explicitly named native-atomic capability delegates to
`toolbox.db.atomic()` and returns one `Deno.AtomicOperation`. The wrapper's
potentially split `atomic()` is a separate opt-in capability and is forbidden
for manifest, identity, namespace, session, page, endpoint, owner, index, or
revision visibility.

`KvToolbox` imports remain confined to the infrastructure implementation.
Domain repository interfaces, services, content/page logic, HTTP adapters,
Fresh routes, islands, components, and site presenters cannot import it or know
its key layout.

This decision refines the safe-interpretation section of [[003.analysis]] and
Phase 1 of [[004.plan]]: existing adapters are rewired incrementally through the
project gateway rather than retaining arbitrary direct `Deno.Kv` access. It
does not change their domain contracts or justify a broad product rewrite.

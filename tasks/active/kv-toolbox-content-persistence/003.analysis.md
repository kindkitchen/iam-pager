# Boundary audit and kv-toolbox assessment

## Sources reviewed

- Repository: <https://github.com/kitsonk/kv-toolbox>
- Reviewed `main` commit:
  `83864f5cba02842a6d186afcdb7cf6a0f060ffe3`
- Latest JSR release on 2026-07-20: `@kitsonk/kv-toolbox@0.31.0`
- Package modules: root toolbox, `blob`, `batched_atomic`, `keys`, `query`, and
  `crypto`
- Local Deno 2.5.0 spike: a 1 MiB value round-tripped through the exact JSR
  release as 17 payload chunks plus metadata and was fully removed.

## The architecture contained the mistake

The product boundaries held. Kvdex appears in implementation-only storage files,
the import map/lock, tests, documentation, and task history. It does not appear
in content/page domain contracts, `PageService`, HTTP adapters, Fresh routes,
presenters, or components. Existing identity, namespace, session, schema
manifest, and selected legacy page repositories use `Deno.Kv` directly and are
not Kvdex implementations.

Therefore this is not a product rewrite. The replaceable area is the unselected
asset prototype plus the not-yet-built durable aggregate. Existing repository
interfaces and backend-neutral conformance are the preservation boundary.

## What kv-toolbox provides

The useful capability is its modular blob API. `set`, `get`, `getMeta`, and
`remove` accept a caller-owned `Deno.Kv`, split binary values into 63,000-byte
parts, and store metadata beneath the caller's key. This fits immutable large
content payloads and lets composition continue to own one Deno KV connection.
The wrapper also exposes the underlying handle as `KvToolbox.db`.

The package does not provide Kvdex-style models or indexes. Page envelopes,
endpoint claims, owner/public indexes, schema validation, and migration remain
adapter-owned raw records. That is desirable: repository invariants stay
explicit and testable rather than becoming library behavior.

## Critical caveats

1. `KvToolbox` is not assignable to `Deno.Kv`. Its `atomic().commit()` returns an
   array because the operation may be split; native Deno KV returns one result.
2. `batchedAtomic()` is not globally atomic when limits require more than one
   commit. It must never implement all-or-none page, endpoint, owner, revision,
   or manifest publication.
3. Blob writes are multi-batch for large values. Interrupted writes can leave
   partial chunks or metadata. The package's blob key is not an application
   visibility marker.
4. Blob reads reconstruct sequential chunks but do not provide the
   application's end-to-end checksum guarantee. The repository must verify its
   own expected byte length and SHA-256 before decoding.
5. Blob APIs accept binary values, not arbitrary `ContentAsset.data`. A narrow,
   versioned storage codec remains required outside the library.
6. `getAsResponse()` is intentionally not used by persistence. It would couple
   the web representation to storage and does not settle the PDF range policy.
7. Query helpers filter after KV listing and are not a substitute for the
   explicit ordered indexes and bounded cursor semantics already required by
   page contracts.
8. Encryption is out of scope. It adds key lifecycle requirements and has an
   open package issue around atomic `setBlob`; adopting it incidentally would
   weaken this correction.

## Progress that can be retained

Retain the current asset protocol and its assertions:

- validate the domain asset;
- encode to detached bytes;
- stage under a random payload identity;
- reconstruct and verify byte length, SHA-256, and decoding;
- publish one immutable manifest with native compare-and-set;
- expose only manifest-backed assets;
- retain payload on an ambiguous manifest exception;
- clean known failed/unpublished staging records best-effort;
- reject corrupt storage on every read;
- prove concurrent single-winner identity creation, cross-instance reads,
  interruption/retry, and legacy-keyspace isolation.

Replace only Kvdex collection/schema calls, encoded key assumptions, and Kvdex
serialization imports. The complete page/endpoint adapter has not been written,
so it can be implemented correctly once rather than translated.

## Safe interpretation of “use kv-toolbox”

Do not mechanically pass `KvToolbox` into every existing repository. That would
change atomic semantics and cause a broad, unnecessary rewrite. Use pinned
kv-toolbox blob capabilities behind a storage-local interface, and retain the
underlying native `Deno.Kv` for single-commit record transactions. Existing
Deno KV repositories that do not need toolbox capabilities remain valid
implementations of their domain interfaces.

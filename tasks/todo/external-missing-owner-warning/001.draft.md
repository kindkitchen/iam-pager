# Owner warning + repair - draft design

## Owner-facing behavior

- Management page view: prominent warning - "External content for this page
  is unavailable (deleted or access revoked at <provider>). Visitors see a
  placeholder." with cause and detected_at. Owner MAY see provider and
  connection names (unlike visitors).
- Creator page list (management + site UI): per-page indicator so a creator
  with many pages spots broken ones without opening each.
- Optional v1+ (record decision if deferred): count surfaced on the
  management dashboard.

## Repair flow (all paths end with `external_missing` cleared)

1. **Re-link** - owner picks/pastes a new provider file reference; system
   stats it via the provider (validates existence + captures integrity),
   creates a new external asset, page replacement points to it.
2. **Re-upload inline** - standard replace flow with inline source.
3. **Detach** - explicit "stop using external storage for this page";
   equivalent to 2 but framed as an action on the warning banner.

No automatic repair, no background polling in v1 - state changes only on
delivery attempts (step 7) and owner actions.

## Work items

1. Management API additions in `lib/page` endpoints (`endpoint.ts`,
   `endpoint-json.ts`, `http.ts`): expose `external_missing`, filter support;
   API contract tests (`routes/api`, `lib/api` matrix) updated.
2. Repair endpoints: re-link (validate via provider `stat_content`),
   replace-inline reuses existing replacement path; tests for both, including
   re-link to a still-missing file (rejected with actionable error).
3. UI: warning banner component + list indicator (components/ + islands/,
   CamelCase); UI-level tests as per existing route test style.
4. Docs: management docs section + CHANGELOG.

## Acceptance

- Owner can go from "content deleted in Drive" to a healthy page via each of
  the three repair paths, fully test-covered.
- Visitors never see provider/connection details at any point.

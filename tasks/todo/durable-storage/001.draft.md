# Durable storage — queued with purpose

## Why this is queued, and why that is fine

This task sits in the backlog deliberately. It is sequenced, not neglected:

- `namespace-reservation` is defining the newest persistence surface
  (namespace ownership) and its atomicity contract. Starting durable backends
  before that shape settles would mean implementing a moving target.
- Deferral is cheap by design. Every store in this codebase already sits
  behind a repository interface (`lib/auth/memory-identity-repository.ts`,
  `lib/session/memory-repository.ts`, `lib/content/memory-repository.ts`, and
  the upcoming namespace repository). Services depend on `interfaces.ts`
  contracts only, so durability is an implementation swap at the composition
  root, not a redesign.
- The in-memory repositories are the first legitimate implementation — not
  mocks, not placeholders. Running them in production is acceptable today
  because "production-grade persistence" is a property of the environment and
  deployment stage, and the whole product is in development. The in-memory
  implementations remain permanently as the reference implementation and the
  fastest test double.

The end state: switchable backends — Postgres, MongoDB, Deno KV, and others —
chosen by configuration at the composition root, with zero changes to service
or domain code.

## What is intentionally NOT decided here

- which repository goes durable first (identity, session, content, namespace);
- which backend is implemented first;
- data migration story between backends;
- retention, cleanup, and backup policy (`OQ-RETENTION`) — stated when a
  durable backend is actually implemented, not before.

## The "how" — fixed technical constraints

1. **Interface pattern is the law.** Every persistence surface is a repository
   contract in `interfaces.ts`. Drivers, clients, and query languages never
   leak into services or domain models. A backend is one new file set
   implementing an existing contract.
2. **Contract test suite over implementations.** One shared,
   implementation-agnostic conformance suite per repository contract, derived
   from the in-memory reference behavior. Every backend must pass the same
   suite; backend-specific tests only add setup/teardown and infrastructure
   concerns. `namespace-reservation` S2 seeds this pattern.
3. **Atomicity is part of the contract, not the backend.** Contracts state
   their concurrency semantics (e.g. namespace reserve is atomic
   check-and-reserve with exactly one winner). Each backend maps that to its
   native mechanism: unique index + insert for Postgres/MongoDB, atomic
   check-and-set for Deno KV. No contract may silently weaken under a backend.
4. **Case-insensitive uniqueness is contract behavior.** How a backend encodes
   it (normalized key column, collation, lowered KV key) is its own business;
   observable behavior — uniqueness across casings, supplied casing preserved —
   is contract-tested.
5. **Repositories own serialization.** Domain models stay storage-agnostic:
   no ORM annotations, no persistence base classes. Thin adapters over drivers;
   prefer std/default solutions per the stack conventions (which makes Deno KV
   the natural first durable candidate — a hint, not a decision).
6. **Selection at the composition root.** Backend choice is environment-driven
   through the existing server-config path. Same application code in every
   environment; an unset choice means in-memory.
7. **No partial adoption inside one repository.** A repository contract is
   served entirely by one backend instance per process; mixing backends across
   different repositories is allowed and expected.

## Unblock condition

Pick this task up after `namespace-reservation` lands its repository contracts
and conformance suite, or earlier if a deployment need forces durability —
in that case start with constraint 2 so the suite exists before the backend.

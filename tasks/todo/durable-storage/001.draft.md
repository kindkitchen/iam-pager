# Durable storage — queued with purpose

Why queued: the namespace contracts are still settling, and deferral is cheap —
every store already sits behind a repository interface
(`lib/auth/memory-identity-repository.ts`, `lib/session/memory-repository.ts`,
`lib/content/memory-repository.ts`, upcoming `lib/namespace/`), so durability
is an implementation swap at the composition root, not a redesign.

Position: in-memory is implementation #1 — legitimate, not a mock, fine in
production while the whole product is in development. It stays permanently as
the reference implementation and fastest test double.

Goal: switchable backends — Postgres, MongoDB, Deno KV, and others — chosen by
configuration at the composition root, with zero changes to service or domain
code.

## How (fixed)

- Every store lives behind an `interfaces.ts` repository contract; drivers and
  query languages never leak into services or models.
- One shared conformance suite per contract, derived from the in-memory
  reference; every backend must pass the same suite.
- Atomicity and case-insensitive uniqueness are contract semantics; each
  backend maps them to its native mechanism (unique index + insert, atomic KV
  check-and-set). No backend may silently weaken a contract.
- Repositories own serialization; models stay storage-agnostic. Thin adapters,
  std/default solutions preferred — Deno KV is the natural first candidate
  (a hint, not a decision).
- Backend selection is environment-driven through server config; unset means
  in-memory.

## What (open until picked up)

Which repository first, which backend first, migration between backends,
retention policy (`OQ-RETENTION` — stated when a durable backend lands).

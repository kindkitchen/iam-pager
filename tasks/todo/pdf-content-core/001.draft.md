# Implement the transport-independent PDF content core

## Objective

Add PDF as one explicit content type, not as a generic binary fallback. The same
validated immutable asset must support browser-native inline delivery and named
attachment delivery through endpoint profiles established by the preceding
contract task.

## Dependency

Start only after `content-endpoint-bindings` has accepted its model, memory
reference, conformance suite, and complete endpoint mapping table.

## Mandatory project invariants

1. Update and settle PDF format/limit specifications before accepting bytes.
2. Define and satisfy focused content/endpoint interfaces; do not branch on PDF
   inside generic page, repository, routing, or UI logic.
3. PDF validation and metadata derivation are pure Deno/TypeScript code with no
   HTTP, Fresh, browser, Deno KV, or Kvdex dependency.
4. Storage receives validated content data; it does not determine MIME type,
   filename safety, endpoint profile, or page authority.
5. Web/API layers will later map these typed contracts and must not become the
   source of PDF behavior.
6. Preserve all existing page authority, revisions, non-disclosure, list/search,
   and `md-page` contracts.
7. Keep README, specs, API notes, CHANGELOG, tests, check, and build synchronized.

## Ordered plan

1. Settle the first PDF byte limit, accepted PDF versions if constrained, and
   minimum structural validation. State clearly that lightweight validation is
   not PDF sanitization or malware certification.
2. Add a `pdf` content handler/capability that accepts a `Uint8Array` and safe
   filename metadata, fixes media type to `application/pdf`, and never trusts
   extension or browser-supplied MIME alone.
3. Keep stored PDF bytes immutable and return a management representation with
   metadata and replace capability; never serialize the complete payload into
   inspection JSON.
4. Implement the PDF endpoint planner/strategy using the settled mapping. It
   emits canonical inline and attachment endpoint intents; the page service
   remains content-type-neutral.
5. Make delivery composition combine intrinsic asset metadata with the resolved
   endpoint profile. Remove the current assumption that presence of a download
   filename alone determines attachment behavior.
6. Define the public preview capability as a URL/model, not embedded PDF bytes.
   Native browser preview is eligible; fallback and PDF.js remain adapter choices.
7. Cover create, inspect, replace, access, rename, duplicate, delete, private
   delivery, and public summary behavior against the memory reference.
8. Run all tests, `deno task check`, and `deno task build`.

## Acceptance

- Non-bytes, oversized input, invalid filename metadata, and inputs failing the
  specified minimum PDF signature/structure are rejected with typed outcomes.
- The handler always derives `application/pdf`; no filename-based MIME inference
  exists.
- Inline and attachment delivery return byte-for-byte identical content and
  endpoint-specific disposition metadata.
- Content inspection exposes bounded metadata, not bytes or storage IDs.
- Replacing PDF content changes both endpoint responses through one revision.
- Renaming and duplication use endpoint-planner interfaces and settled conflict
  behavior.
- PDF aliases do not appear as independent managed/public/exploration pages.
- No PDF branch is added to Fresh routes or Preact components.

## Not in this task

Multipart parsing, HTTP byte ranges, Kvdex persistence, browser components,
PDF.js, thumbnails, text extraction/search, generic raw binary, or external
storage.

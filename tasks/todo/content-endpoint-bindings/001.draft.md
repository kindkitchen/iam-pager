# Separate pages, content assets, and delivery endpoints

## Objective

Establish the smallest interface-first domain change needed for one PDF payload
to be reachable through browser-preview and attachment URLs without becoming two
managed pages or two independently updated copies.

## Confirmed direction

- A page remains the stable management, revision, access, tagging, listing, and
  exploration identity.
- A page has one canonical locator and may have alternate endpoint bindings.
- An endpoint binds a locator to the page plus a delivery profile such as
  `inline` or `attachment`.
- The page points to one immutable content asset. Multiple endpoints resolve the
  same asset bytes; physical duplication is not required by the contract.
- Endpoint URL generation is supplied by a strategy. Core page behavior and HTTP
  must not infer attachment behavior from `.pdf`.
- Alternate endpoints never produce extra management or exploration rows.

This deliberately corrects the unsafe interpretation "store the PDF twice".
Two physical records would not provide the requested one-content-to-many-locator
relationship and could diverge during replacement, access change, or deletion.

## Mandatory project invariants

1. Specifications are authoritative. Resolve `OQ-PDF-ENDPOINTS` and update the
   semantic markers before freezing code contracts.
2. Define interfaces and typed outcomes before implementations. Domain and
   application code must not import Fresh, Preact, `Request`, `Response`, Deno
   KV, or Kvdex.
3. The memory implementation is the reference and a shared conformance suite is
   mandatory before a durable adapter.
4. Repositories own atomic identity, locator, endpoint, and revision conditions;
   services own validation, authorization, and publication plans.
5. HTTP and site code remain secondary projections and make no authority,
   collision, disposition, or content-lifecycle decisions.
6. Preserve namespace authority, private non-disclosure, revisions, ETags, CSRF,
   visitor-safe summaries, and existing `md-page` behavior.
7. Update README, specification, API documentation where applicable, CHANGELOG,
   tests, check, and build with each delivered change.

## Decisions to freeze before code

Document an exhaustive endpoint mapping table covering:

- named canonical `example` and the working attachment alias `example.pdf`;
- a default page with no page name;
- a canonical name already ending in `.pdf`;
- case-insensitive collision with another canonical or alternate endpoint;
- rename into or away from any of those cases;
- whether unchanged aliases preserve publisher casing;
- returned canonical, preview, and download link semantics.

Working assumptions are deterministic generation and whole-operation conflict:
if any required endpoint is occupied, create/rename fails without choosing a
surprise suffix and without partial visibility.

## Ordered plan

1. Move the PDF endpoint edge rules from open questions to a settled table. Do
   not change code first.
2. Model logical page identity, immutable content identity, canonical endpoint,
   alternate endpoint, and delivery profile as transport/storage-neutral types.
3. Introduce focused interfaces for endpoint planning, content asset access, and
   atomic page/endpoint persistence. Prefer capability interfaces over one broad
   repository implementation type.
4. Specify create, resolve, replace, rename, duplicate, access-change, and delete
   outcomes, including all-or-none endpoint collision behavior.
5. Implement the memory reference and backend-neutral conformance suite.
6. Refactor `PageService` and current `md-page` flow onto the contracts without
   changing its public JSON/API behavior; an `md-page` initially has only its
   canonical inline endpoint.
7. Update owner/public projections to expose one page and explicit safe endpoint
   links while excluding aliases from list/search order and cursors.
8. Run all existing tests plus new concurrency and cardinality coverage, then
   `deno task check` and `deno task build`.

## Required conformance

- Both endpoint locators resolve the same page ID and content asset ID.
- Delivery profile differs while content bytes remain identical.
- Private/non-owner resolution is non-disclosing through every endpoint.
- Create and managed takeover publish every required endpoint or none.
- Concurrent endpoint claims have one complete winner.
- Rename moves the complete endpoint set or leaves the old set unchanged.
- Content replacement switches one page asset reference observed by all
  endpoints; mixed old/new visibility is impossible.
- Access/tag changes increment once and affect one page, not endpoint rows.
- Duplicate semantics for immutable asset sharing are explicit and safe.
- Delete removes all endpoint visibility without deleting an asset still in use.
- Managed/public lists and exploration return the logical page exactly once.
- Existing default/named `md-page`, revision, rename, duplicate, storage, HTTP,
  and UI tests remain green.

## Not in this task

PDF byte validation, upload transport, Kvdex, PDF browser rendering, generic
binary files, quotas, text extraction, and external storage.

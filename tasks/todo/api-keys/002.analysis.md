# Current boundary and selected direction

## Current state

- The specification and page API explicitly support only browser sessions and
  currently say external API bearer credentials do not exist.
- Root request middleware extracts a cookie through `SessionTransport` and
  resolves every request to a guest or authenticated `Session`.
- Namespace and page HTTP adapters derive owner identity directly from that
  session and enforce browser CSRF themselves. Guest `POST /api/pages` remains a
  deliberate trial-publication capability.
- Identity/namespace ownership, sessions, and pages already use interface-backed
  memory and Deno KV implementations with conformance-oriented tests.

## Critical correction

An API key is not another browser session transport. A key has its own ID,
secret hash, label, permissions, expiry, update revision, and revocation
lifecycle; it has no logical session, OAuth attempt, idle renewal, cookie, or
CSRF token. Synthesizing a `Session` from a key would couple automation to
browser lifecycle and invite CSRF bypasses.

Introduce a raw API authentication resolver and an authorization principal/policy
interface. It resolves either the existing browser session or an API key into a
user actor plus credential kind and permissions. Application services continue
to receive server-derived user IDs; Fresh only forwards the resolved context.
Browser session behavior outside `/api` stays unchanged.

## Contract decisions for specification link

- Use the standard `Authorization: Bearer <api-key>` header on `/api/**` only.
  Never accept keys in query strings, bodies, cookies, site/direct-content
  routes, or `/auth/**`.
- If an Authorization header is present, it is authoritative. Malformed,
  unknown, expired, or revoked keys return one non-disclosing `401` with an
  appropriate Bearer challenge; a valid cookie must not become fallback.
- Use explicit `read`, `write`, and `delete` permissions. Accept `all` only as
  input shorthand for the complete current set and return/store the expanded
  set, so future permissions are not silently granted.
- `read` covers owner API reads; `write` covers reservation, create, update,
  rename, duplicate, and access mutations; `delete` covers page deletion/bulk
  deletion and API-key revoke-all. Resource authority and page revisions remain
  mandatory after permission checks.
- API-key list/create/inspect/update/individual-delete require a browser
  authenticated session regardless of permissions. Browser mutations require
  CSRF. Bearer credentials never satisfy those operations. Collection
  `DELETE /api/api-keys` is the only bearer-accessible key operation and requires
  `delete`.
- API keys never enter guest behavior. In particular, bearer page creation is a
  managed owner create and never trial publication.
- Generate at least 256 random secret bits, return the bearer once on create,
  persist only a SHA-256 lookup hash, and make metadata endpoints unable to
  recover it. Rotation is create-new then delete-old.
- Metadata includes an opaque key ID, non-empty bounded label, explicit sorted
  permissions, `expires_at` as a future timestamp or `null`, creation/update
  times, revision, and status. Duplicate labels are allowed. Expired metadata
  remains browser-manageable but cannot authenticate.
- Update and individual delete use strong revision ETags. Revoke-all is one
  linearizable owner operation. A per-owner key generation/epoch is the likely
  Deno KV design so an unbounded set becomes invalid atomically without relying
  on one oversized delete transaction.
- Do not record `last_used_at` in this scope: a write on every authenticated
  request adds contention and is not required by the requested lifecycle.

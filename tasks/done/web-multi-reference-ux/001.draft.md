# Align the web with multi-reference pages

## Context

The page domain and API now model one logical content item with one non-empty set of locator references. References may cross namespaces owned by the same creator, the preferred reference is only for stable management/exploration links, and PDF references independently select `inline` or `attachment` delivery.

The current web projection predates that contract. It still requires PDFs to have a preferred inline endpoint and a mandatory attachment alternate, rejects cross-namespace and larger valid sets in client logic, uses the legacy one-locator Markdown request, resubmits endpoints during PDF content replacement, and recognizes only the old PDF pair in management/public views.

## Scope

### Publishing and references

- Replace format-specific canonical/alternate assumptions with a presenter-owned reference editor used by Markdown and PDF publishing.
- Require one primary path and permit zero or more removable optional aliases. UI copy must state that aliases are additional URLs for the same logical page/content, not copies.
- Submit explicit `endpoint_set` requests for new Markdown and PDF publications.
- Keep page name optional for primary and alias locators.
- Do not require a PDF alias, an inline preferred reference, an attachment reference, or one shared namespace.
- Do not recreate Deno KV's current eight-reference capacity as a product/UI validation rule. Present server capacity failures accurately.
- Consume server/presenter-declared content-format and delivery-profile capabilities instead of embedding domain rules in components.

### PDF delivery control

- Show a `Downloadable` checkbox for each PDF locator reference.
- Map checked to the `attachment` profile and unchecked to `inline`; do not infer behavior from a suffix or whether a row is an alias.
- Make clear that one URL has one delivery profile. A user who wants both browser opening and direct download adds a second optional alias and gives the two references different checkbox values.

### Creator namespaces

- Supply owned namespace reservations through a server-owned publishing view model without exposing identity/session internals.
- For signed-in creators, render namespace selection from their owned namespaces for the primary path and every alias. Allow different owned namespaces across references.
- If the creator owns no namespace, disable managed publication with a clear path to reserve one rather than falling back to guest publication.
- Keep guest namespace controls as the existing free-text field with random-name support.
- Apply the same owned-namespace source anywhere management permits selecting a destination namespace; filtering controls may remain search/filter inputs when they are not mutation destinations.

### Management and public projections

- Render every returned reference and its actual delivery profile for Markdown and PDF; do not assume the preferred reference is inline or that attachment references are alternates.
- Let creator reference edits replace the complete endpoint set under revision/ownership checks.
- Ensure content-only Markdown or PDF replacement omits `endpoint_set` and preserves all references.
- Keep rename behavior explicit as preferred-page-name-only, and ensure duplicate/reference-edit controls do not silently discard aliases.
- Present current API failures without obsolete same-namespace, mandatory-download, preferred-inline, or fixed-count explanations.

### Dedicated exploration page

- Add `/site/explore` as the canonical public exploration page, including search, clearing, pagination continuation, empty/error states, and breadcrumbs.
- Remove the exploration panel from the publishing/home view.
- Add an `Explore` destination to site navigation for guests and creators, alongside relevant home/manage/session actions, with accessible current-page state.
- Point exploration forms, result continuation URLs, and clear links at `/site/explore`.
- Preserve old query-bearing `/` and `/site` exploration links through a documented redirect to the canonical route so bookmarks do not silently become publishing-page URLs.

## Acceptance criteria

- A Markdown or PDF can be created in the web UI with one locator and no alias.
- Optional aliases can be added/removed and may use any namespace owned by the creator.
- A one-locator PDF can be either inline or downloadable; an inline plus downloadable pair is possible only by explicitly adding a second locator.
- Creator namespace mutation fields are selects sourced from current owned reservations; guest behavior is unchanged.
- Management and exploration show one logical item while exposing all of its delivery links accurately.
- PDF content replacement preserves references unless the user explicitly edits them.
- Exploration is a dedicated navigation destination and no longer occupies the home publishing page.
- Presenter/unit/component/route tests cover guest and creator behavior, one/many references, cross-namespace aliases, both PDF profiles, content-only replacement, and exploration redirects/navigation.
- `deno task verify` and `deno task build` pass.
- `README.md`, `docs/api/pages.md`, relevant specification files (including resolving `OS-UI-REFERENCES`), and `CHANGELOG.md` describe the shipped web behavior.

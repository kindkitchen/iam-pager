# Namespace contracts (direction step 1)

## The direction: namespace reservation (DS-PROTECT)

An authenticated creator reserves a unique namespace; reservation blocks guest
and cross-user writes; publishing checks ownership. Delivery and guest
publishing into unreserved namespaces keep current behavior.
Spec anchors: `DA-NAMESPACE`, `DA-LOCATOR`, `CP-NAMESPACE`, `OQ-AUTH`.

| Namespace  | Guest publish | Owner   | Other authenticated |
| ---------- | ------------- | ------- | ------------------- |
| unreserved | allowed       | allowed | allowed             |
| reserved   | rejected      | allowed | rejected            |

Steps, each its own task, created as the previous one completes:

1. **Contracts — this task**
2. Reservation service + publishing authorization (the business core)
3. HTTP API + site UI
4. Conformance check against the spec + docs

## This step

`lib/namespace/` following the existing lib layout (model / interfaces /
memory-repository):

- `NamespaceReservation` model: namespace as supplied, owner user id,
  reserved_at;
- `NamespaceRepository` contract: atomic reserve — exactly one winner under
  concurrent attempts, typed `taken` for losers; case-insensitive lookup;
  list by owner;
- in-memory implementation;
- conformance test suite, implementation-agnostic so `durable-storage`
  backends can reuse it later.

Done when: the memory implementation passes the suite — reserve, duplicate
rejected across casings, supplied casing preserved, owner listing, concurrent
reserve yields one winner — and the contract documents its atomicity and case
rules.

## Constraints

- Interface-first; no HTTP concepts in this layer.
- Namespace validity reuses the locator-engine rules so reservation and
  publishing can never diverge (`DA-NAMESPACE`).
- Spec priority: divergent implementation is rejected; to change direction,
  update the spec first, then continue.

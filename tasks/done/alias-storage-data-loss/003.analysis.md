# Persistence selection caused the disappearance

The alias mutation path itself preserves the page's immutable asset reference and updates page plus endpoint projections atomically. The focused memory/Deno KV repository, service, and HTTP suites passed 103 tests, including endpoint replacement and repository reconstruction.

The runtime configuration is unsafe instead:

- the local `.env` has `DENO_KV_ID` and `DENO_KV_ACCESS_TOKEN` but no `IAM_PAGER_*_STORAGE_BACKEND` selectors; those values do not select application repositories;
- `Deno.openKv()` without an explicit remote URL does not use `DENO_KV_ID` in local Deno;
- commit `7927ce0` renamed the documented deployed page selector from `IAM_PAGER_CONTENT_STORAGE_BACKEND` to `IAM_PAGER_PAGE_STORAGE_BACKEND` without compatibility handling, so an existing deployment could silently fall back to page/asset memory;
- a read-only audit of the configured remote database found durable identity, namespace, session, and API-key records, but zero page-aggregate or content-asset records in any iam-pager page/content keyspace.

Cloud restarts or multiple isolates therefore explain the observed correlation: adding an alias was a normal atomic page update, while subsequent requests no longer saw process-local state. Data already lost with the memory process is not recoverable from this KV database.

Implement legacy-selector compatibility, fail-closed runtime selection when persistence must be explicit, clear remote-KV guidance, and an alias/reconstruction regression test.

# Existing boundaries and implementation decisions

## Correction from the earlier framing

An earlier, discarded framing incorrectly treated public/private behavior,
private non-disclosure, guest limitations, and creator management scope as open
product questions. Those are already specified. It also scoped the application
around what the current publishing island could render.

This task reverses that dependency: raw TypeScript contracts and services define
page behavior; HTTP is the first complete representation; site UI is optional
and cannot grant authority or constrain the model.

## Current implementation gaps

- `PageRecord` has no stable management ID, owner/trial provenance, access, or
  revision.
- `ContentRepository` is locator-keyed `get`/unconditional `put`/`delete`; it
  cannot list, distinguish trial from managed content, enforce create conflicts,
  or perform revision-bound updates.
- `PublishingService.publish` is an ambiguous create-or-replace operation for
  guests and creators alike.
- Direct delivery receives no actor and therefore serves every stored page.
- The page API is one flat MdPage POST body; there is no list, inspect, update,
  or delete resource contract.
- Editable source exists in `MdPageData`, but no content-handler interface
  converts stored data back to a management-safe input representation.
- Authenticated page publishing does not validate the session synchronizer
  token.
- Deno KV content storage is optimized around locator-keyed envelopes/chunks and
  has no page-ID, owner, or list index.
- Several specification implementation-status paragraphs still describe
  namespace/API/content persistence as future or process-local.

## Decisions applied by the plan

### Stable management identity

Add an opaque route-safe `page_id`. The direct locator remains the public content
identity and URL; page ID exists only for management. This supports the already
specified future rename operation without making API resource URLs change when a
direct locator changes.

### Explicit stewardship

Every record is either:

- `trial`: always public and not owned; or
- `managed`: carries the creator user ID that established it under a reserved
  namespace and may be public or private.

The user ID is never accepted from or returned to the client. Namespace
reservation remains required for every managed mutation; stored stewardship
supports owner indexing and atomic prevention of trial-over-managed writes.

### Explicit mutation semantics

- Guest POST is trial create-or-replace and requires `access: "public"`.
- Authenticated POST is managed create, requires the caller's reserved
  namespace and exact CSRF token, replaces a trial at the locator, and conflicts
  with an existing managed page.
- PATCH changes only fields explicitly present (`content`, `access`) and requires
  the current ETag. Omitted fields remain unchanged atomically; there is no
  ambiguous default.
- DELETE requires the current ETag.
- Managed reads/listing derive the owner from the resolved session.

### Optimistic concurrency

A positive integer revision is part of the page model and management response.
The HTTP ETag encodes page ID plus revision. PATCH/DELETE require exact
`If-Match`; missing preconditions return 428 and stale revisions return 412.
Repository operations check revision and stewardship atomically, so concurrent
mutations have one winner and never mix content/access.

### Trial/reservation overlap

No cross-repository namespace/content transaction is introduced. Instead, the
page repository atomically enforces that trial writes can replace only absent or
trial records, while managed create can replace a trial. Therefore an in-flight
trial write cannot overwrite a managed page that has already landed: it returns
the typed reserved/managed conflict and the client keeps its draft. A trial that
lands before managed creation is simply replaced. The remaining window in which
a trial lands after reservation but before the first managed page is accepted as
part of trial's no-guarantee behavior and cannot destroy managed content.

### No legacy migration

This is development without production records. Introduce the new page keyspace
and schema directly; old locator-envelope records are not read or migrated.
Legacy local databases may be deleted. The new repository starts its own schema
at version 1 and tests only the new contract plus rejection of malformed current
records.

### API before UI

The complete acceptance surface is service and HTTP API behavior. Existing site
publishing receives only the minimum request-shape/CSRF changes needed to keep
public publishing functional and preserve drafts on errors. No page-management
component, access selector, list, or editor-loading flow belongs to this task.

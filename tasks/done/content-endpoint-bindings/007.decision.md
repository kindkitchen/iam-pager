# Stage immutable assets before atomic page visibility

The second active-task increment introduces the split persistence model without
yet changing the composed API:

- `ContentAsset` has its own opaque identity, intrinsic content data/meta, and
  creation time. Creation is immutable: an existing ID conflicts and is never
  overwritten; reads are internal capabilities and page operations do not
  delete assets.
- Asset creation is a staging step. Atomic page publication accepts only an
  already-complete asset ID, allowing a future segmented durable adapter to
  finish bytes before any endpoint can expose them.
- `PageAggregate` stores page identity/policy/revision, one current asset ID, and
  the complete canonical/alternate endpoint set. Focused interfaces cover asset
  create/read, page read, endpoint resolution, trial/managed creation, combined
  revision-bound endpoint/content/access/tag mutation, same-namespace
  duplication, and deletion.
- Managed creation, endpoint replacement, and duplication may retire all
  endpoint-occupying trials in the same complete commit but reject any foreign
  managed claim. Trial replacement preserves one intersected trial's identity;
  a set intersecting several separate trials rejects as `endpoint_conflict`
  rather than unexpectedly collapsing pages.
- Content replacement flips one page asset reference observed through every
  endpoint. Duplication receives fresh page/endpoints but shares the immutable
  source asset. Deletion removes all page endpoint visibility and deliberately
  retains the asset for safe sharing and later bounded garbage collection.
- `MemoryPageAggregateRepository` is the process-local reference. Its shared
  16-case conformance suite covers structural rejection, boundary isolation,
  staged visibility, same-namespace mutation, complete endpoint conflicts,
  takeover and moves, concurrent claims, coherent asset switches, access/tag
  updates, owner/revision checks, duplication, trial replacement, and deletion
  retention.

The existing `PageService`, `PageRepository`, raw-Deno-KV adapter, HTTP, and JSON
representations remain unchanged and continue serving one canonical inline
`md-page` endpoint. Next: refactor that application behavior onto the split
capabilities, retaining compatibility before adding PDF or Kvdex. Verification:
all 473 tests, check, and the production build pass.

# Freeze bounded endpoint-set planning

The first active-task increment settled and implemented the generic endpoint-set
policy before changing page persistence:

- one binding is structurally canonical and zero to seven are alternates;
- every locator is ordinary publisher intent, validated independently, unique
  case-insensitively, and inside the canonical endpoint's namespace;
- canonical status does not imply a delivery profile;
- the fixed profile vocabulary is `inline` and `attachment`, while every content
  type declares its non-empty supported subset; `md-page` is inline-only and PDF
  will support both;
- alternate submission order is non-semantic and normalized by locator identity;
- publisher spelling remains part of the returned binding;
- `.pdf` and every other suffix remain behavior-free;
- add/change/remove/canonical/casing mutation replaces the complete set against
  the exact page revision and repository publication must be all-or-none;
- managed creation may retire endpoint-occupying trials only as one complete
  commit, while any foreign managed claim rejects the complete operation;
- duplication receives fresh destination endpoints but may share the immutable
  source asset safely.

`PageEndpointPlanner` and `DefaultPageEndpointPlanner` now encode the pure
transport/storage-neutral planning boundary with focused tests. The existing
stored page model, repositories, service, HTTP, and API deliberately retain their
single canonical inline endpoint until the next increment introduces immutable
content asset identity and atomic page/endpoint aggregate contracts with a memory
reference and shared conformance suite.

# Review: locator layer and content interfaces

Reviewed the code landed with [[003.analysis]]: `lib/locator/*`,
`lib/content/*`, 23 tests, `deno task check` clean.

## Holds up

- Strategy/engine split works as intended: `PathSlugStrategy` stayed a pure
  mapping, and the forbidden-namespace policy provably applies to any future
  strategy (engine tests cover it independently of strategy behavior).
- Resolution unions force route handlers to branch on
  `not_a_locator | invalid_segment | forbidden_namespace`, which maps cleanly
  onto the QT-ROUTING outcomes (serve site / 4xx / serve site alias).
- Roundtrip test (`format` then `resolve`) pins the bidirectional contract,
  including encoding and casing preservation.

## Flaws found, accepted for now

1. **`/` as page-name separator leaks into the model.** `Locator.page_name` uses
   `/` as the canonical multi-slug separator, which is a path-shaped assumption
   at model level. Accepted: some canonical separator is needed for
   strategy-independent identity; `/` is documented on the field. A subdomain
   strategy must still map to/from it.
2. **`locator_key` can collide across sources.** The key joins namespace and
   page name with `/`, so a namespace containing `/` would collide with a page
   path. `path-slug` cannot produce one (embedded slashes are rejected), but
   nothing at model level forbids constructing such a `Locator` by hand. Fix
   belongs to the deferred charset validation: forbid `/` in `namespace` at
   model level when validation lands.
3. **Asymmetric error model.** `resolve` returns unions (untrusted input);
   `format`/unknown-strategy throw (programmer error: the app should never hold
   a forbidden or unmapped locator to format). Intentional, but worth
   remembering when the publish flow is written.
4. **Case folding is `toLowerCase()`.** No Unicode full case folding or locale
   handling (Turkish dotless-i class of issues). Fine while the allowed charset
   is undecided; revisit together with charset validation.
5. **`ContentTypeHandler.derive` is synchronous.** MdPage derivation is sync,
   but a future type (image processing, external fetch) may need
   `Promise<Data>`. Changing the signature later is cheap while there is one
   implementer; flagged rather than pre-generalized.
6. **Repository stores no original-cased locator.** `ContentRepository` is keyed
   by the lowercased key, but DA-LOCATOR requires returning publisher-supplied
   casing. The publish step will need a page record that carries the original
   `Locator` alongside the `ContentRecord` — likely a `PageRecord` wrapper; the
   repository interface may grow to store it.

## Verdict

Interfaces are sound for the next step. No rework needed before implementing
MdPage and the in-memory repository; items 2 and 6 must be addressed within this
task before the guest flow is declared done.

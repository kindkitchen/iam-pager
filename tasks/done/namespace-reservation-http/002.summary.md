# Namespace reservation reaches creators over HTTP and site UI

Delivered DS-PROTECT namespace-reservation steps 3 and 4.

- Added interface-backed `NamespaceHttpHandler` / `NamespaceHttpAdapter` and
  thin `/api/namespaces` route. Authenticated `GET` lists only the caller's
  reservations in deterministic oldest-first order; authenticated `POST`
  accepts bounded JSON, requires the session synchronizer token, and maps
  manager results to typed HTTP errors. Responses are no-store and successful
  claims return the direct path and ISO reservation time.
- Added `CreatorNamespacePanelPresenter`, which keeps session decisions,
  repository reads, ordering, path formatting, and trusted CSRF inputs outside
  Fresh/components. The server-rendered site hides the panel for guests and
  gives creators an island with owned reservations and an inline reserve form.
- Wired `/api/pages` to derive `PublishActor` from the resolved request session.
  A creator can therefore use a newly reserved namespace; guests and other
  creators remain blocked by `NamespacePublishingAuthorizer`.
- Generalized `GuestPublishForm` to `PagePublishForm` and corrected environment-
  independent and creator-specific protection copy.
- Updated README, changelog, and QT-API/current-state specification guidance.
- Added 17 tests across the namespace HTTP adapter, panel presenter, and
  session-derived publishing actor. `deno task check`, all 307 tests, and
  `deno task build` pass.

Remaining DS-PROTECT work is page management/access behavior, not namespace
reservation: private/public state, inspection, deletion, and management UI.

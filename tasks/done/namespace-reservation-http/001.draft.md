# HTTP API + site UI for namespace reservation (DS-PROTECT step 3)

Continuation queued by [[namespace-reservation-service]]: the business layer
(`NamespaceReservationManager`, `NamespacePublishingAuthorizer`) is wired but
unreachable over HTTP; creators cannot yet reserve a namespace.

## Scope

- `lib/namespace/http.ts` — `NamespaceHttpHandler` interface plus adapter over
  `NamespaceReservationManager`:
  - `POST` reserve: authenticated sessions only, JSON body, bounded buffering,
    synchronizer CSRF token in the body compared against the session token,
    typed mapping of `ReserveNamespaceResult` (201, 401, 403, 409, 415, 422).
  - `GET` list: authenticated sessions only, owned reservations with public
    paths, oldest first.
- `routes/api/namespaces.ts` — thin route delegating to the adapter.
- `lib/ui/namespace-panel.ts` — presenter deciding panel visibility and
  building the creator model (csrf token, reservations with locator-engine
  paths) so UI components stay logic-free.
- `islands/NamespaceReservationPanel.tsx` — creator panel on the site page:
  owned list plus reserve form posting to the API.
- Composition-root wiring, conformance-style tests for adapter and presenter.

## Out of scope

- Page management under a reserved namespace (later DS-PROTECT slices).
- Releasing or transferring reservations (no service support yet).
- Step 4 (spec conformance pass + docs sweep) stays a separate task.

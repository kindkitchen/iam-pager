# Current completed project baseline

The authoritative requirements remain `README.md`, `docs/specification/`, and
`docs/api/pages.md`. This summary is the compact task-level context for choosing
future work; it contains completed state rather than delivery history.

## Product

`iam-pager` publishes supported content at deterministic namespace and optional
page-name locators. Direct paths return content itself. The site is a separate
projection for publishing, wrapped viewing, public exploration, namespace
reservation, and creator management. The platform does not assign meaning or
relationships to pages.

A visitor can open known public content, use a safe site wrapper, and browse
public creator pages. A guest can publish a public, undiscoverable trial in an
unreserved namespace, with no ownership or overwrite guarantee. Google sign-in
establishes an application user; namespace reservation separately establishes
publishing authority. Creators can manage public or private pages only in owned
namespaces.

## Page and content model

A logical page has one stable management ID, immutable current asset, access
policy, tag set, revision, management row, and exploration row. It has one
canonical endpoint and up to seven alternates in the same namespace. Each
endpoint explicitly selects `inline` or `attachment`; paths and filename
suffixes have no delivery meaning. Endpoint, asset, access, tag, and projection
changes are revision-bound and atomic.

Managed operations cover creation, inspection, listing and filtering, updates
to content, access, tags, and endpoints, rename, duplication, bulk access and
deletion, and single deletion. Trial replacement, managed takeover of trials,
endpoint collision, concurrent winner, and stale-revision behavior are explicit.
Missing, private, invalid, and unauthorized visitor lookups collapse to a
non-disclosing 404.

Current content handlers are:

- `md-page`: bounded Markdown and optional CSS, with sanitized HTML derived at
  publication and inline delivery;
- `pdf`: bounded detached bytes, portable filename metadata, structural PDF
  screening, and byte-identical inline/attachment delivery with validators and
  one byte range.

## Interface boundaries

Product behavior lives under `lib/`, independent of Fresh and components:

- `LocatorEngine` validates and formats transport-independent locators through
  a mapping strategy;
- `PageService` owns publishing, authority, management, delivery, and public
  query behavior;
- `PageAggregateRepository` is the sole page persistence contract for assets,
  pages, endpoint claims, and owner/public projections;
- focused identity, namespace, session, authentication-strategy, transport,
  content-handler, presenter, and HTTP interfaces isolate their concerns;
- presenters produce complete bounded view models; components render them and
  prepare requests without deciding authority or persistence behavior;
- Fresh routes resolve request context, select an adapter operation, and map its
  result without reimplementing application rules.

Interface-satisfying implementations remain valid even when one composition does
not select them. No disconnected historical page adapter, service compatibility
branch, migration/readiness path, or generic database-release framework remains.

## Persistence and composition

Memory is the reference implementation for all repositories. Deno KV provides
durable identity/namespace, session, and page implementations behind the same
interfaces. Identity plus namespace ownership are composed as one persistence
unit. Durable sessions and pages require durable ownership and inherit its KV
path so protected state cannot outlive its authority.

`KvPageAggregateRepository` stores strict page envelopes, endpoint claims,
owner/public projections, and verified manifest-backed content. Content is
staged and verified before publication; page visibility uses one native atomic
commit. Corrupt or unknown records fail closed. There is no data-copy,
migration, rollback, or compatibility system; a future incompatible storage
change requires an explicit project decision.

Current durable selectors are:

- `IAM_PAGER_OWNERSHIP_STORAGE_BACKEND=deno-kv`;
- `IAM_PAGER_SESSION_STORAGE_BACKEND=deno-kv`;
- `IAM_PAGER_PAGE_STORAGE_BACKEND=deno-kv`;
- optional shared `IAM_PAGER_OWNERSHIP_DENO_KV_PATH` for self-hosting.

## Sessions, authentication, and HTTP security

Every routed request has a typed guest/authenticated session and server request
ID. Opaque bearer transport is separate from storage. Credentials and OAuth
state use 256-bit entropy; repositories store bearer/state hashes. Sign-in
consumes a bounded one-use attempt, finds or creates the provider identity,
upgrades the logical session, and rotates the bearer. CSRF-bound logout revokes
it and creates an unrelated guest session.

Google authentication supports explicit original mode and loopback-only local
mock mode. A narrowly allowlisted HTTPS preview host may derive callback URLs
from the validated request host; `Origin` and `Referer` are never authorities.
Provider tokens, callback values, cookies, and provider failures do not enter
presentation or diagnostics.

Fresh-independent HTTP adapters enforce bounded strict JSON/multipart shapes,
CSRF, strong revision ETags, request-body limits, status mapping, isolation,
disposition, cache policy, and PDF range behavior. Direct active content does
not receive the platform shell. Wrapped Markdown is sandboxed and no-referrer;
PDF uses a browser-native viewer with explicit direct/download/fallback links.

## Site projection

The mobile-first site includes guest/creator publishing, namespace reservation,
creator page management, public exploration, and wrapped page views. Markdown
editing keeps raw source authoritative while offering Raw/Steps section editing,
lossless fenced blocks, drag/keyboard ordering and merge behavior, CSS editing,
local draft preview, adaptable layout, and fullscreen preview. PDF publishing
and replacement use bounded file-selection helpers and explicit endpoint intent.
Unknown server detail is discarded; stale mutations refresh state without silent
retry.

## Verification boundary

The current suite contains 454 tests. Shared conformance runs against memory and
Deno KV page aggregates and the corresponding namespace, identity, and session
repositories. Regression coverage protects current locator, authority, session,
page lifecycle, endpoint, asset, query privacy, strict HTTP, PDF byte/range,
presenter, component, corruption, and concurrency behavior. `deno task verify`
and the production Fresh build pass at this baseline.

## Deliberate open scope and risks

Not implemented: total quotas, publishing rate limits, guest expiry, account
deletion, backups/retention guarantees, orphan-asset sweeping, full-text indexes,
relevance/view sorting, generic binary or active content, PDF text extraction or
PDF.js, external storage, and automatic storage migration/rollback.

Memory storage is process-local. Deno KV must be selected explicitly where
continuity matters. Local fake authentication must remain loopback-only or on a
narrow non-production preview allowlist. PDF validation is structural screening,
not malware certification. Any future active content or external provider must
preserve isolation, authority, privacy, endpoint, and atomic page semantics.

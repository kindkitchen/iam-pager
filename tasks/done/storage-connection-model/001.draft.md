# Storage connection model - draft design

## Pattern to mirror

`lib/auth`: `IdentityRepository` interface +
`identity-repository-conformance.ts` + `memory-identity-repository.ts` +
`kv-identity-repository.ts`. Same four-piece layout here.

## Model

```ts
export interface StorageConnection {
  readonly connection_id: string; // opaque, route-safe
  readonly user_id: string; // local ApplicationUser id
  readonly provider_id: string; // "google-drive"
  readonly provider_subject: string; // provider account subject
  readonly scopes: readonly string[]; // granted, as returned by consent
  readonly status: "active" | "revoked";
  readonly created_at: Date;
  readonly updated_at: Date;
}
```

Rules:
- Keyed lookups needed: by `connection_id`, by `(user_id, provider_id)`, list
  by `user_id`.
- v1 uniqueness: one ACTIVE connection per (user_id, provider_id);
  reconnecting the same provider replaces tokens on the existing record when
  `provider_subject` matches, otherwise the old connection is revoked first.
- `status: "revoked"` is kept (not deleted) so assets referencing the
  connection can explain WHY they are missing.
- Tokens (refresh/access + expiry) live in a separate KV record encrypted at
  rest (key from env, e.g. `IAM_PAGER_STORAGE_TOKEN_KEY`); repository API
  exposes `get_credentials(connection_id)` to providers only - never through
  management surfaces.

# Reservation service + publishing authorization (direction step 2)

## Direction context

Namespace reservation (DS-PROTECT): an authenticated creator reserves a
unique namespace; reservation blocks guest and cross-user writes; publishing
checks ownership. Spec anchors: `DA-NAMESPACE`, `DA-LOCATOR`, `CP-NAMESPACE`,
`OQ-AUTH`.

| Namespace  | Guest publish | Owner   | Other authenticated |
| ---------- | ------------- | ------- | ------------------- |
| unreserved | allowed       | allowed | allowed             |
| reserved   | rejected      | allowed | rejected            |

Steps: 1 contracts (done, `namespace-reservation-contracts`), **2 this
task**, 3 HTTP API + site UI, 4 conformance check + docs.

## This step

- Reservation service on top of `NamespaceRepository`:
  - reserve: validate the namespace through the locator engine (namespace-only
    locator; forbidden namespaces and malformed segments rejected with typed
    reasons) before attempting the repository reserve;
  - typed results the API layer can map without string parsing;
  - list a user's reservations.
- Publishing authorization implementing the table above, applied where
  publishing decides whether a write may proceed (above `ContentRepository`,
  which stays protection-free by contract). Guest publishing into unreserved
  namespaces keeps current behavior.
- Tests for both: validity delegation, reserve outcomes, each cell of the
  authorization table.

## Constraints

- Interface-first; no HTTP concepts in this layer.
- Runs entirely on the in-memory repository; durable backends swap in later
  behind the same contract.
- Spec priority: divergent implementation is rejected; to change direction,
  update the spec first, then continue.

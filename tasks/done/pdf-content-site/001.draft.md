# Add the PDF publishing and viewing site projection

## Objective

Complete "Ability to create page with PDF content" through the site without
moving PDF, endpoint, authority, or storage rules into Preact. A publisher can
select PDF content, publish one page, open its browser-native preview, and use an
explicit download link; a creator can inspect metadata and revision-bound replace
that PDF.

## Dependency

Start only after `pdf-content-http` publishes an accepted strict contract and the
composed API/direct lifecycle passes.

## Mandatory project invariants

1. Web-independent presenters/request builders/response validators precede
   components and islands.
2. Components render models and collect intent only. They do not validate PDF
   structure, generate endpoint aliases, choose disposition, infer authority, or
   manipulate storage identity.
3. Browser PDF support is an adapter capability with a visible fallback; the
   page remains usable when inline rendering is unavailable.
4. Existing mobile-first `md-page` publishing/editing and creator management
   remain intact rather than being generalized through unsafe UI conditionals.
5. Private access, CSRF, ETag/revision conflicts, no silent retries, and safe
   creator-content isolation remain unchanged.
6. Update README, specs, API documentation, CHANGELOG, presenter/component tests,
   browser smoke, full tests, check, and build together.

## Ordered plan

1. Add a pure content-type presentation model and request preparation boundary
   for choosing Markdown or PDF and preparing the accepted PDF upload contract.
2. Add a bounded file-selection UI with filename/size feedback. Client checks are
   advisory; server validation remains authoritative.
3. Preserve draft/selection state on API errors and show typed alias, PDF, size,
   authority, stale revision, and storage failures without exposing internals.
4. Extend creator page rows/inspection with PDF metadata, canonical preview,
   download, and revision-bound replacement actions; do not attempt to edit bytes
   as JSON/source text.
5. Extend the public wrapper presentation model with a PDF preview URL and
   attachment link. Render the browser-native viewer using the accepted secure
   embed/object/iframe approach and always provide direct-preview and download
   fallbacks.
6. Keep alternate endpoints out of exploration and related-page lists while
   displaying the logical page's PDF type and size once.
7. Add responsive keyboard-accessible controls and browser tests for native
   success, unavailable preview fallback, download, Back navigation, private
   denial, replacement, and deletion.
8. Run full tests, `deno task check`, `deno task build`, and composed local
   acceptance from authentication/namespace reservation through PDF lifecycle.

## Acceptance

- Guest/creator PDF availability follows the accepted application/API policy;
  the browser never invents authority.
- Publishing returns and visibly distinguishes preview and download actions for
  one page.
- Browser-native preview loads the canonical endpoint when supported; a clear
  fallback remains when not.
- Download uses the server-provided attachment endpoint and filename.
- Creator inspection shows metadata without loading bytes into JSON; replacement
  is exact-revision-bound and stale state refreshes without silent retry.
- Access changes and deletion affect preview and download together.
- Public exploration and creator management each show one logical page, never an
  alias duplicate.
- Existing Markdown editor/publisher/management behavior remains covered and
  unchanged.

## Not in this task

PDF.js, annotations, thumbnails, text extraction/search, generic file upload,
external storage, or unrelated visual redesign.

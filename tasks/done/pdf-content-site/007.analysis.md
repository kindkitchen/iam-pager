# Split the site UI along web navigation with breadcrumbs

## Direction

Today `/` and `/site` render one monolithic `SiteApp` that stacks hero,
exploration, namespace reservation, page management, and the publish form. The
PDF projection adds publish/inspect/preview/replace/download surface that would
overload that single screen. Direction: give each job a real route and a
server-owned breadcrumb trail (home -> section -> item) so back/forward/home use
native history and every state is deep-linkable.

## Why it fits

- Invariant 1: a breadcrumb trail is a pure server model, like the existing
  `SiteNavigation`. Presenters build it; components only render. Web stays one
  projection of raw logic.
- Each route hydrates only the island it needs, shrinking per-screen surface as
  PDF actions arrive.
- SSR-friendly, shareable URLs, per-page focus and accessibility.

## Critical view

- Do not over-split. Breadcrumbs earn their place only where hierarchy is real
  (manage -> page -> replace). The common guest "publish one page" path must
  stay shallow and reachable from home.
- Per-route islands move state through props/URL, not client memory, adding
  server round-trips. Acceptable, but keep a draft inside the island that owns
  it.
- The trail must be server-derived so it never leaks authority; return_to, CSRF,
  ETag/revision conflicts, and private access stay unchanged.

## Plan impact

Add a navigation foundation before the view work: extend `SiteNavigation` with a
`trail` breadcrumb Interface plus presenter, then split management and per-page
inspection/replacement into routes while keeping publish on the landing. The
public view already lives at `/site/<locator>`.

## Open question

How deep to split now: minimal (breadcrumb model + split management/inspect) vs
full (separate routes for publish, manage, inspect, replace). Recommend
incremental — land the breadcrumb Interface first, split where hierarchy is
real, defer the rest.

# Explicit pre-deploy and schema-upgrade foundation completed

Implemented the exact Deno 2.9 task-object graph: check, the complete test suite,
and production build are sibling dependencies; the uncached database-schema
command runs only after all succeed; the commandless `pre-deploy` task completes
last. The schema command has only its required environment and filesystem
permissions and remains outside application startup and requests.

Added storage-neutral schema plans, steps, state repository, upgrader, bounded
report, and safe error contracts. The runner snapshots a bounded immutable
registry, requires stable IDs and adjacent positive versions, preflights every
plan and initial durable state before writing, atomically claims only the exact
next transition, resumes retained pending helpers, completes only a matching
claim, and fails closed on gaps, downgrades, future/unsupported versions,
unknown claims, corruption, and non-converging contention. There is no rollback
or inferred diff. A pending claim is not a process mutex, so helpers are required
to be repeat-idempotent and concurrency-safe.

Added a versioned Deno KV state adapter using versionstamp checks for baseline
initialization, claims, and completion, plus an implementation-agnostic
conformance suite. The current immutable registry defines independent
`ownership`, `sessions`, and `pages` schemas. Missing framework metadata means
the documented raw-KV baseline version 1 for fresh and existing databases; all
current targets are version 1, so installation does not inspect or rewrite
application records and repeated durable runs report `no_change`. Memory
profiles open no database.

The thin CLI reuses linked ownership/session/page storage validation, opens the
ownership KV through a focused factory, closes owned resources, and emits only
bounded schema IDs, versions, step IDs, and outcomes. README, specification,
deployment guidance, and CHANGELOG now describe the implemented behavior and
overlapping-run requirement.

Verification passed: all 454 tests, `deno task check`, `deno task build`, two
repeated `pre-deploy::upgrade-db-schema` invocations, and the complete
`deno task pre-deploy` gate.

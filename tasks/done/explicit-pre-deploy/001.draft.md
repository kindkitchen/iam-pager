# Add explicit pre-deploy and forward-only schema upgrades

## Objective

Provide one manually invoked deployment gate and a small reusable schema-upgrade
framework. It detects a required database change by comparing code's declared
target version with durable schema state, applies only explicit forward
transformations, and becomes a successful no-op after the database reaches the
target. No rollback framework or automatic runtime migration is wanted.

## Accepted boundaries

- `deno task pre-deploy` is explicit; application startup and requests never run
  schema upgrades.
- Independent verification runs in parallel where Deno's dependency graph permits.
- Schema detection is version-based, not an attempted automatic diff of stored
  values or TypeScript models.
- Upgrade plans and the runner are storage-agnostic interfaces/raw logic.
- Deno KV is the only first storage/coordination implementation.
- Every transformation is one-way and idempotent. It may safely resume after an
  interruption or repeated invocation.
- There are no down migrations, rollback commands, or hidden automatic cleanup.
- One-off helpers may be retired only after all supported deployments are known
  to be newer than their source version; removing them immediately would break
  delayed environments.

## Mandatory project invariants

1. Update specifications before implementation if any behavior changes.
2. Define focused interfaces and typed outcomes before concrete Deno KV or CLI
   composition. Deno KV types do not enter the runner contracts.
3. Keep deployment orchestration in `deno.json` and a thin script; migration
   planning/idempotency/concurrency logic lives in raw TypeScript.
4. The Deno KV adapter must satisfy an implementation-agnostic conformance suite.
5. Do not weaken current repository contracts or couple migrations to Fresh,
   Preact, routes, or web presentation.
6. Use the import map, Deno/std defaults, kebab-case files, snake_case data, and
   interface-satisfying implementations.
7. Keep README, specifications, deployment guidance, CHANGELOG, tests, check,
   and build synchronized.

## Required Deno task graph

Use task objects and exact dependency names, not shell background operators and
not a wildcard dependency:

```jsonc
{
  "$schema": "https://deno.land/x/deno/cli/schemas/config-file.v1.json",
  "tasks": {
    "pre-deploy": {
      "description": "Verify and upgrade before deployment",
      "dependencies": ["pre-deploy::upgrade-db-schema"]
    },
    "pre-deploy::check": {
      "description": "Run formatting, lint, and type checks",
      "command": "deno task check"
    },
    "pre-deploy::test": {
      "description": "Run the complete test suite",
      "command": "deno task test"
    },
    "pre-deploy::build": {
      "description": "Build production output",
      "command": "deno task build"
    },
    "pre-deploy::upgrade-db-schema": {
      "description": "Apply missing forward database-schema upgrades",
      "command": "deno run <least required permissions> scripts/pre-deploy/upgrade-db-schema.ts",
      "dependencies": [
        "pre-deploy::check",
        "pre-deploy::test",
        "pre-deploy::build"
      ]
    }
  }
}
```

Deno runs check/test/build in parallel, then runs the schema command only after
all succeed. The commandless parent completes after that dependency. Keep the
upgrade task uncached because its decisive input is external database state.
Users can bound dependency concurrency with `deno task --jobs <n> pre-deploy` or
`DENO_JOBS`.

## Core contracts

Define names only after reviewing current module boundaries, but preserve these
capabilities:

- `DatabaseSchemaUpgrader` — execute all declared schema targets and return a
  bounded report (`upgraded`, `resumed`, or `no_change` per schema).
- `SchemaUpgradeStep<Context>` — stable step ID, exact `from_version`, exact
  `to_version`, and an idempotent forward transform.
- `SchemaUpgradeStateRepository` — read state, atomically claim one expected
  transition, and atomically mark that same claim complete.
- an immutable plan/registry — stable `schema_id`, declared target version, and
  the complete contiguous steps needed from every supported version.

A persisted state must distinguish completed current version from a claimed
pending transition. The claim includes enough stable identity to resume exactly
the same helper after a crash, never a newly reordered function.

## Required runner behavior

1. Validate all plans before any storage write: stable unique schema/step IDs,
   positive/explicit versions, contiguous forward edges, one path to target, no
   duplicate edge, no downgrade, and no target below durable state.
2. Read one schema state. Treat the documented baseline consistently for a fresh
   or pre-framework database.
3. Return `no_change` without transformation when current equals target.
4. If a known transition is pending, resume its same idempotent helper.
5. Otherwise atomically claim only the next step from the exact expected current
   state. A concurrent loser re-reads rather than applying blindly.
6. Apply the helper. Helpers update records idempotently and use adapter checks
   where partial data changes could race.
7. Atomically mark completion only for the matching claim, then continue to the
   next step.
8. On failure, leave the claim resumable and exit non-zero. Do not mark complete,
   advance another step, or attempt rollback.
9. Reject unknown pending IDs, missing historical helpers, gaps, corruption, or
   incompatible future database versions before mutation.
10. Emit bounded diagnostics containing schema IDs, versions, step IDs, and
    outcomes only—never stored values, paths with secrets, or credentials.

## Deno KV implementation

- Store upgrade state in an adapter-owned, versioned keyspace separated from
  application repositories and user data.
- Use Deno KV versionstamp checks/atomic commits for first initialization,
  transition claim, and matching completion.
- Support independent `schema_id` values so ownership, session, page, or future
  repositories can evolve without one global fake version.
- Share an injected `Deno.Kv` instance and remain testable across adapter
  instances.
- Define baseline behavior for existing raw-KV databases without rewriting
  application data merely to install the framework.
- Do not add a rollback log. A retained pending transition is resume state, not
  rollback state.

## Upgrade composition

The thin `scripts/pre-deploy/upgrade-db-schema.ts` composition should:

1. load the same validated storage environment needed to select the target Deno
   KV database;
2. open/receive that database through a focused factory interface;
3. register current schema plans and one-way helper functions;
4. run the generic upgrader once;
5. print a bounded summary and exit non-zero on any unsafe/incomplete result;
6. close owned resources reliably.

With no missing step it must still execute, inspect durable state, print an empty
or no-change summary, and succeed. Do not use Deno task `files` caching for this
command.

## Verification

Shared core/adapter tests must cover:

- empty/current plan returns no change;
- first baseline initialization for fresh and existing databases;
- one and several contiguous upgrades in exact order;
- a deployment that skips several application versions;
- repeat invocation performs no transformation;
- failure before any write, midway through an idempotent helper, and after data
  changes but before completion all resume safely;
- two concurrent runners cannot apply one transition unsafely;
- completed state and pending claims survive a new repository/process instance;
- gaps, duplicates, downgrade, future version, unknown pending step, and corrupt
  state fail closed;
- CLI composition selects the expected database and returns correct exit status;
- the Deno task graph runs check/test/build concurrently and never starts schema
  upgrade after a failed dependency.

Final gates: full tests, `deno task check`, `deno task build`, repeated local
`pre-deploy::upgrade-db-schema`, and complete `deno task pre-deploy`.

## Not in this task

Any actual application-data schema migration beyond installing/validating the
current baseline, rollback, automatic model diffing, startup migration, Kvdex,
PDF work, a migration web UI, or external database implementations.

# Gated replacement plan

Each phase is a reviewable checkpoint. Do not combine cutover or record cleanup
with the first dependency replacement.

## Phase 0 — Freeze behavior and establish the safety baseline

1. Keep `IAM_PAGER_CONTENT_STORAGE_BACKEND=deno-kv` on the current
   `DenoKvPageRepository`; do not route runtime traffic to the new adapter.
2. Record the current full test/check/build baseline and retain focused Kvdex
   tests until equivalent replacement tests pass.
3. Inventory all Kvdex imports, exports, physical-prefix assumptions, docs, and
   lockfile roots. Classify historical changelog/task references separately so
   history is not rewritten.
4. Add architecture assertions to the review checklist:
   - no kv-toolbox import outside `lib/storage` and storage-focused tests;
   - no storage type in content/page contracts, services, HTTP, routes, islands,
     or components;
   - no `Response` creation in persistence;
   - no migration during startup, build, deploy, or ordinary requests.
5. Keep the existing Kvdex commit intact in history. Replacement happens as new
   work; do not reset or destructively rewrite the completed checkpoint.

**Gate:** unchanged baseline is green and the replacement surface is listed.

## Phase 1 — Introduce narrow storage capabilities

1. Pin exact `@kitsonk/kv-toolbox@0.31.0` imports through `deno.json`; avoid a
   floating range for durable layout behavior.
2. Add a storage-local binary-object interface with only the operations the
   repository needs, for example stage/set, read, metadata/readability check,
   and remove. Its values are bytes and its keys are adapter-owned; it knows
   nothing about pages, endpoints, HTTP, or PDFs.
3. Implement that interface with named exports from
   `@kitsonk/kv-toolbox/blob` over a caller-owned `Deno.Kv`. Do not expose the
   concrete package type from the interface.
4. Add a versioned content-data codec interface (`encode`/`decode`) so
   `ContentAsset.data` is not coupled to kv-toolbox's binary API. Initially
   preserve the proven V8 round-trip or extract the existing tagged codec; make
   the selected format explicit in the manifest and test its Deno 2.5/runtime
   compatibility before choosing. Do not silently change encoding.
5. Continue using the existing `KvDatabaseOpener` and raw handle unless a
   smaller connection capability is demonstrably needed. Avoid wrapping every
   native KV method merely to rename it.
6. Add contract tests for the blob implementation: empty/invalid input policy,
   1 MiB and maximum-PDF-sized round trips, fresh wrapper instances, partial
   write cleanup, missing metadata/chunks, truncation, and removal.

**Gate:** the package is pinned and isolated; native atomic operations remain
separate and tests demonstrate the blob failure model.

## Phase 2 — Replace the immutable-asset prototype first

1. Create an adapter-owned keyspace such as:
   - manifests: `iam-pager/content-assets/v1/by-id/<asset_id>`;
   - staged payloads:
     `iam-pager/content-assets/v1/payloads/<random_payload_id>` with
     kv-toolbox-owned suffixes below that key.
   Exact keys become constants in one storage module and never enter domain
   types.
2. Preserve a strict manifest containing schema/encoding version, asset and
   payload identities, encoded byte length, SHA-256, content type, media type,
   declared size, optional filename, and creation time.
3. On create:
   - validate and detach the asset;
   - check for an existing valid manifest;
   - encode once and calculate hash/length;
   - write bytes under a random, unreachable payload key with kv-toolbox;
   - read back through a fresh-capable path and verify length, hash, and decode;
   - publish the manifest with raw `Deno.Kv.atomic().check(absent).set(...)`;
   - on a known lost race/failure, remove the staged payload;
   - on an exception with ambiguous manifest outcome, retain the payload.
4. On read, resolve the manifest first, validate every field and key identity,
   read the payload, and repeat length/hash/decode/domain validation. Partial or
   malformed state is corruption, not “not found.”
5. Port the existing focused tests before deleting their Kvdex versions. Add the
   accepted 16 MiB PDF case and failure injection at multiple blob batches.
6. Only after parity is green, remove the Kvdex asset/database files, exports,
   imports, and lock roots. Rename implementation/tests to library-neutral or
   kv-toolbox names; domain interfaces remain unchanged.

**Gate:** no Kvdex runtime dependency remains, asset behavior is at least as
strong as before, and deployment composition is still unchanged.

## Phase 3 — Implement the durable page aggregate with native atomics

1. Promote the existing focused capability intersection to a named
   `PageAggregateRepository` interface in raw page code. `PageService`, memory,
   conformance, and storage factories depend on that interface, never on a
   concrete durable class.
2. Implement a Deno KV aggregate adapter/facade that composes:
   - the kv-toolbox-backed content-asset repository;
   - adapter-owned aggregate records and explicit indexes;
   - raw `Deno.Kv.atomic()` for every visibility mutation.
3. Use one authoritative page envelope by stable page ID. Store only the asset
   reference plus page state and the complete canonical/alternate endpoint set;
   do not duplicate payload bytes per endpoint.
4. Maintain explicit case-normalized endpoint claims and ordered owner/public
   indexes. Alternate endpoints never become extra management/exploration rows.
5. For create, trial replacement, managed takeover, combined update, rename,
   duplicate, and delete, check all relevant current entries and mutate the page
   plus every affected endpoint/index in one native commit. With at most eight
   endpoint bindings, keep a tested margin below Deno KV transaction limits.
6. Asset publication precedes page publication. Page commits check a valid
   manifest entry and reference only immutable assets; page deletion does not
   delete potentially shared assets.
7. Reuse validation, cursor, retry, corruption, and index-coherence patterns
   from `DenoKvPageRepository`, and behavioral algorithms from
   `MemoryPageAggregateRepository`. Do not use kv-toolbox query filtering to
   replace deterministic indexes.
8. Run the shared aggregate conformance unchanged. Add durable-only tests for
   restarts, malformed records, index drift, contention exhaustion, all eight
   endpoint claims, transaction-limit headroom, and injected commit races.

**Gate:** memory and durable implementations satisfy the same named interface
and conformance; no batched atomic participates in page visibility.

## Phase 4 — Add non-destructive schema-v1 compatibility

1. Treat the existing raw `iam-pager/pages` schema as production data, not as
   disposable Kvdex input.
2. Prefer a shadow schema-v2 keyspace for aggregates/assets. Do not mutate or
   delete schema-v1 records during the first migration; this keeps a failed or
   retried migration from breaking the currently selected adapter.
3. Add one retained, adjacent, repeat-safe `pages-v1-to-v2` migration to the
   manual database schema registry. It must:
   - validate each legacy envelope/index/chunk set;
   - derive deterministic asset/payload identities for retry safety;
   - copy and verify each content payload through the new asset adapter;
   - map the legacy locator to one canonical inline endpoint;
   - write the aggregate and indexes conditionally/idempotently;
   - detect conflicting pre-existing v2 data rather than overwrite it;
   - leave v1 source records untouched.
4. Add an explicit v2 readiness/sentinel rule or equivalent factory probe. A
   selected new adapter must fail clearly on an unmigrated non-empty v1 database
   instead of returning an empty site. This is a compatibility check, not an
   automatic migration.
5. Test empty baseline, real schema-v1 fixtures, mixed trial/managed/private
   records, retries after interruption at each stage, concurrent migration,
   corrupt source, conflicting destination, absent manifest, and no-op rerun.
6. Document operator order: backup, `db:check`, explicit `db:update`, verify,
   change/select deployment, smoke test. No rollback claims are made; retained
   v1 records provide a deliberate fallback window.

**Gate:** migration is repeat-safe, source-preserving, and cannot silently hide
legacy data.

## Phase 5 — Controlled composition cutover

1. Update the page repository factory to return the named aggregate interface
   for durable v2 storage while preserving memory behavior and configuration
   validation. Identity, namespace, and session factories remain unchanged.
2. Keep the service's legacy `PageRepository` compatibility path until the
   migration fixtures and deployment fallback have been exercised. Removing it
   is a later explicit cleanup, not a prerequisite for safe selection.
3. Prove that ownership, sessions, pages, and the schema task share the intended
   database/path without sharing concrete library types.
4. Run all service, HTTP, presenter, route, and component tests unchanged. Only
   composition tests should know that durable selection changed.
5. Run `deno task verify`, `deno task build`, and focused manual schema checks on
   disposable local databases before marking the adapter selectable.

**Gate:** explicit durable selection uses the new aggregate, all behavior is
green, and rollback to the untouched v1 selection remains operational during
the agreed window.

## Phase 6 — Final cleanup and documentation

1. Confirm no live `@olli/kvdex`, Kvdex key-prefix, class, import-map, or lockfile
   dependency remains. Keep only immutable historical changelog/task references.
2. Update README, specification, database operations, and storage comments with
   exact kv-toolbox responsibilities and the native-atomic exception.
3. Record known orphan policy: unpublished random payloads are unreachable and
   cleanup is best-effort; a bounded reconciler is separate work unless required
   before public traffic.
4. Do not delete legacy v1 data in this task. Retention/deletion requires a
   separate approved task after backup and rollback requirements are settled.
5. Unblock `pdf-content-http` only when the cutover gate is met. HTTP range,
   disposition, ETag, and response streaming remain in its raw-code adapter,
   never in Fresh components or the blob repository.

## Final acceptance checklist

- Exact kv-toolbox release pinned; Kvdex absent from live code and dependencies.
- kv-toolbox types and blob layout confined to storage implementation.
- Existing domain/application/web interfaces do not expose the library.
- Native Deno KV atomic commits preserve full page/endpoint/index visibility.
- Blob staging cannot publish a partial asset; every read checks length/hash.
- Maximum accepted PDF survives persistence and restart within documented
  limits.
- Shared aggregate conformance and durable fault tests pass.
- Legacy v1 migration is manual, adjacent, repeat-safe, source-preserving, and
  refuses incompatible/unmigrated selection.
- Runtime/deploy performs no automatic migration or destructive cleanup.
- README, CHANGELOG, specification, and all related open tasks agree.

# Expose strict PDF upload and delivery HTTP boundaries

## Objective

Let callers create and revision-bound replace a PDF page, receive its canonical
preview and attachment links, and retrieve identical PDF bytes with the endpoint-
specific HTTP behavior defined by the pure application model.

## Dependencies

Start after `pdf-content-core` and `kvdex-content-persistence` pass their
acceptance gates. The adapter may also run against memory for tests, but must not
invent missing core/storage semantics.

## Mandatory project invariants

1. Settle `OQ-PDF-TRANSPORT` and update the API specification before routes.
2. Multipart/body parsing, headers, URLs, ranges, and `Response` stay in the HTTP
   adapter. Core PDF input is bytes plus validated metadata, never base64 JSON.
3. Existing `md-page` JSON requests remain compatible.
4. Actor, namespace authority, CSRF, exact ETag/revision, private non-disclosure,
   strict schema, no-store, and bounded diagnostics remain unchanged.
5. Endpoint links and disposition come from application presentation contracts;
   the route does not append `.pdf` or decide inline versus attachment.
6. Fresh files remain thin delegates. The site is not implemented here.
7. Update API docs, specs, README, CHANGELOG, tests, check, build, and composed
   smoke coverage together.

## Ordered plan

1. Choose a strict bounded multipart form or dedicated upload endpoint. Specify
   exact fields, media types, filename rules, byte limits, duplicate/unknown
   part handling, malformed boundaries, and status/error mappings.
2. Decide HTTP range behavior based on the first PDF size limit and native viewer
   smoke: implement correct single-range `206`/`416` behavior or explicitly
   specify bounded full-body `200` delivery and defer ranges.
3. Add a routing-independent decoder that bounds bytes before constructing the
   pure PDF command. Do not rely only on `Content-Length`.
4. Extend create and revision-bound replacement while preserving session-derived
   trial/managed semantics, owner authority, CSRF, and `If-Match`.
5. Extend inspection/presentation with safe PDF metadata and explicit endpoint
   links; never return PDF bytes or asset/storage IDs in JSON.
6. Map canonical endpoint delivery to `application/pdf` plus `inline`, and the
   alternate endpoint to the same bytes plus a safely encoded `attachment`
   filename. Preserve length, nosniff, cache, request ID, and session boundaries.
7. Ensure private, missing, malformed, corrupt, and unauthorized access is
   non-disclosing through both endpoints.
8. Add thin Fresh route wiring only after adapter tests.
9. Run full tests, check, build, and a composed create/preview/download/replace/
   stale/private/delete lifecycle.

## Acceptance

- Oversized or malformed multipart input is rejected before application
  mutation, including chunked bodies and misleading length headers.
- Filename and client MIME cannot override PDF validation or response media type.
- Create returns one page with canonical inline and attachment endpoint URLs.
- Both endpoint bodies are byte-identical; disposition and filename differ as
  specified.
- Managed replacement requires exact current ETag and changes both endpoint
  responses once; stale requests never partially mutate.
- Private-page behavior is identical and non-disclosing at every endpoint.
- Alias conflicts map a typed whole-publication failure; HTTP does not generate a
  fallback URL.
- Existing Markdown create/manage/delivery contracts and tests remain green.
- Native browser preview is smoke-tested under the chosen full/range policy.

## Not in this task

Preact upload UI, PDF.js, thumbnailing, PDF text search, generic binary upload,
external storage, quotas, or unrelated API credentials.

# PDF content core complete

Implemented and registered the transport-independent `pdf` handler. It accepts
detached `Uint8Array` content up to 16 MiB, recognizes PDF 1.0–1.7 and 2.0 after
byte-zero header plus terminal xref/EOF checks, validates portable filenames up
to 255 UTF-8 bytes, fixes `application/pdf`, and supports inline and attachment
profiles. Management inspection exposes bounded filename/media-type/size/version
metadata without payload bytes.

Generic page application contracts now accept either the compatible one-inline
locator or complete endpoint-set intent. Complete sets are planned through the
content handler's profile declaration, persisted atomically, and replaced under
the exact page revision. Reordering identical alternates is a no-op; content
replacement must remain compatible with retained profiles; canonical rename
preserves every alternate; endpoint-aware duplication requires a fresh complete
destination set. Typed conflicts and the legacy repository's endpoint-set limit
fail without partial mutation.

Focused lifecycle tests cover managed and trial creation, inspection, endpoint
replacement, content/access changes, no-op ordering, conflicts, rename,
duplication, one-row projections, exact inline/attachment bytes, legacy
rejection, and deletion. All 493 tests, check, and production build pass.

Next in the PDF chain: `kvdex-content-persistence`, followed by strict HTTP PDF
transport and the secondary site projection.

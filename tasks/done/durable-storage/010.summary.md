# Durable content slice delivered; every repository now has a durable backend

Added `DenoKvContentRepository` implementing `ContentRepository` with the
envelope-plus-immutable-generation-chunks layout of [[009.decision]]: versioned
envelope per locator, 48 KiB JSON data chunks per generation, checked atomic
envelope flips that delete the replaced generation, retry-based contention
handling, and corruption distinguished from concurrency by envelope
versionstamp comparison.

Extracted the bespoke memory-repository tests into
`lib/content/repository-conformance.ts` and ran `MemoryContentRepository` and
`DenoKvContentRepository` through it, including multi-chunk round-trips,
small/large replacement residue, and concurrent one-winner puts. KV-specific
tests additionally pin the stored envelope/chunk shape, exact chunk-boundary
splitting, generation cleanup on replace and delete, cross-instance sharing,
JSON-unserializable rejection, invalid-envelope rejection, and
missing-chunk corruption detection.

Environment composition adds `IAM_PAGER_CONTENT_STORAGE_BACKEND` behind
`ContentRepositoryFactory` in `lib/storage/content-storage.ts`, defaulting to
memory and accepting `deno-kv` only with Deno KV ownership, inheriting its
path/default database. `create_app_services` accepts an injected
`content_repository`; the configured composition parses and wires it. Updated
README production guidance, DA-LIFECYCLE, and QT-STORAGE, and logged the change
in CHANGELOG (29 new tests, 290 total).

With users, provider identities, namespace reservations, sessions, and now
content all selectable between the memory reference and Deno KV, the task's
goal — durable persistence behind existing repository interfaces with
environment-selected backends — is met. Remaining operational limits stay
documented as future work outside this task: no ownership expiry/deletion, no
backend migration, no application-managed backup, no orphan-chunk sweeper.

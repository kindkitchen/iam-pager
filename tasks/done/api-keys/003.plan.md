# Specification-first implementation chain

Complete links in order. Every link must keep logic in interface-backed raw code,
keep Fresh/routes/components free of business and authorization decisions, use
strict bounded inputs and outputs, update README/specification/API docs and
CHANGELOG where behavior changes, and add its own tests before proceeding.

## 1. Freeze the product and API contracts

- Add API-key invariants to product, capability, experience, security,
  authentication, storage, and verification specifications.
- Add `docs/api/authentication.md` for cookie-versus-Bearer resolution,
  precedence, CSRF policy, errors, and the permission matrix.
- Add `docs/api/api-keys.md` for browser-owned CRUD and bearer revoke-all; update
  page/namespace API references so every current operation names its required
  permission and remove the obsolete no-bearer statement.
- Fix exact bounds and representations: key/label/permission limits, one-time
  secret response, nullable expiry, statuses, ETags, request sizes, method/media
  behavior, and stable error codes. State that `all` expands to the current
  explicit permission set.
- Explicitly preserve guest trial publication only for a guest browser context;
  the API-key subsystem itself has no guest behavior.

Coverage/gate: documentation consistency review, no contradictory bearer/CSRF
claims under README or `docs/`, then `deno task check`.

## 2. Implement the transport-independent key lifecycle

- Add API-key model, generators, clock use, repository interfaces, focused
  lifecycle interfaces, and service under `lib/api-key/`.
- Implement create, owner list/inspect, revision-bound metadata update,
  individual revoke, resolve-by-bearer, and atomic owner revoke-all outcomes.
- Keep raw bearer material only inside creation/resolution boundaries; hash
  before repository access and compare secret-derived values safely.
- Enforce label, permission, expiry, owner isolation, active generation, and
  revision rules in raw code rather than HTTP or UI.

Coverage/gate: model/service tests for every validation and outcome, one-time
secret exposure, expiry boundaries with a fake clock, owner isolation, stale
revisions, permission expansion, collision retries, immediate revoke, and
concurrent create/revoke-all linearization; `deno task test` for the new module.

## 3. Add conforming memory and Deno KV persistence

- Build the memory reference repository and one shared API-key repository
  conformance suite.
- Build a strict Deno KV implementation using the ownership database so key user
  references cannot outlive durable identities. Use an owner generation/epoch
  (or an equivalently linearizable interface-satisfying design) for immediate,
  unbounded revoke-all.
- Validate every stored field and fail closed on malformed records. Keep only
  hashes, metadata, owner indexes/generation, and revocation state; never store
  the returned bearer.
- Wire repositories through ownership storage factories and app composition;
  memory remains the default and durable ownership selects durable keys.

Coverage/gate: run the same create/read/update/revoke/resolve/revoke-all,
clone-safety, ordering, corruption, expiration, stale-write, collision, and
concurrency cases against memory and Deno KV; add storage selection/composition
tests; `deno task test`.

## 4. Expose browser-session key management HTTP

- Add a Fresh-independent API-key HTTP handler and thin routes for
  `GET|POST|DELETE /api/api-keys` and
  `GET|PATCH|DELETE /api/api-keys/:api_key_id`.
- Restrict list/create/inspect/update/individual-delete to the owner derived from
  an authenticated browser session. Require `x-csrf-token` on browser
  mutations; require strong `If-Match` on update and individual delete.
- Return the full bearer only in a successful create response. All later
  representations expose bounded metadata only. Keep collection delete bodyless
  and make its all-key revocation atomic.
- Keep strict methods, media types, schemas, unknown-field rejection, body
  bounds, no-store responses, safe errors, ETags, and non-disclosing ownership.

Coverage/gate: HTTP tests for every method/auth/CSRF/ETag/media/body/error branch,
one-time bearer visibility, foreign IDs, expiry edits, revoke-all, repeated
requests, and response secrecy; route thinness/composition tests; `deno task
test`.

## 5. Resolve Bearer principals and authorize every existing API operation

- Add an API request authenticator and policy interface that produces guest,
  browser-user, or API-key principals without manufacturing a browser session.
- Accept strict Bearer authorization only under `/api/**`; make an explicitly
  supplied invalid bearer fail without cookie fallback. Do not issue or renew a
  session cookie solely for a bearer request.
- Refactor page and namespace HTTP contexts to consume the API principal/policy.
  Browser mutations retain CSRF; API-key mutations require the mapped permission
  and no CSRF. Domain owner/namespace/revision checks remain unchanged.
- Apply the documented matrix to namespace list/reserve and every page
  collection/item/action/bulk operation. A key-authenticated create is always
  managed. Permit only `DELETE /api/api-keys` from a key principal with delete;
  reject all other key-management paths regardless of its grants.
- Preserve browser guest publication and all browser/session/auth/site/direct
  behavior. Key authentication does not expose private direct-content delivery.

Coverage/gate: resolver and policy table tests for malformed/duplicate schemes,
header precedence, invalid/expired/revoked keys, each permission combination,
`all` expansion, CSRF differences, and revoke-all self-invalidation; integration
coverage executes every current owner API operation with allowed and denied
keys and proves existing browser/guest regressions unchanged; `deno task test`.

## 6. Add the secondary web projection

- Add a presenter/view model and authenticated management component that use the
  completed API for list/create/edit/delete/revoke-all. Components receive no
  owner ID and make no permission, expiry, or authority decisions.
- Show a newly created bearer once with explicit copy/store guidance; do not put
  it in a URL, persistent browser storage, later render model, diagnostics, or
  analytics. Require explicit confirmation for revoke-all.
- Keep the site optional: removing the component must not remove any API-key
  capability or rule.

Coverage/gate: presenter and component tests for complete bounded models,
create-once secret handling, stale revision recovery, expired status, CSRF
submission, revoke-all confirmation, failure mapping, and proof that components
do not infer authorization; focused UI tests and `deno task test`.

## 7. Close the regression and documentation boundary

- Update README with the final bearer usage example, permission semantics,
  storage behavior, and security warning; reconcile all specification/API
  links and CHANGELOG entries with the implemented contract.
- Search for stale claims that API credentials do not exist or that every API
  mutation always requires CSRF.
- Review credential redaction and ensure no test fixture teaches query/body key
  transport.

Coverage/gate: `deno task verify`, `deno task build`, and a final contract matrix
showing browser owner, guest browser, valid scoped key, expired/revoked key, and
invalid explicit bearer behavior for every API endpoint.

# Corrected live Deno Deploy integration gaps

The first deployment screenshot separated three partition outcomes: revision
preview correctly skipped pre-deploy but failed its independent runtime warmup;
Git Branch/master failed configuration because Build variables do not enter the
Development timeline context; Production accepted storage configuration but
could not open attached Deno KV.

The attached database is exposed to Deno CLI pre-deploy through an injected
remote default path and `DENO_KV_ACCESS_TOKEN`. Deno 2.5 requires explicit token
environment and network permissions for that remote backend. The pre-deploy task
now grants both while retaining only read-only checker operations. The manual
remote updater now permits dynamic data endpoint hosts returned by its strictly
validated `api.deno.com` metadata URL instead of incorrectly allowing only that
initial host.

The schema configuration check now also rejects ownership-only durability rather
than silently accepting memory sessions or pages. README and QT-PREDEPLOY place
backend variables in Production and Development, never Build, and retain the
revision-preview process-memory override.

Verification passed: all 475 tests, formatting/lint/type checks, and production
build. Remaining external check: deploy with the backend selectors in Production
and Development, the ownership KV path absent, and valid authentication settings
in each runtime context. A fresh database should then report `unversioned`
rather than `invalid_configuration` or `database_unavailable`.

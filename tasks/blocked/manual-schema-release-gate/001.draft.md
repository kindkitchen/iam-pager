# Move verification and schema mutation out of deployment

## Objective

Keep Deno Deploy pre-deploy small and non-mutating. Local pushes and GitButler
review creation run check and tests through a native pre-push hook. Deployment
only reads an attached database manifest and fails before routing when the
project identity or any schema version is not exactly current. A developer with
an explicit remote database URL and access token runs the retained forward
upgrade utility separately.

## Settled boundaries

- Deno Deploy does not run formatting, lint, type checks, tests, or another build
  in pre-deploy. The platform build remains its own stage.
- No CI service is added. A tracked native pre-push hook is installed locally;
  GitButler `but push` and `but pr new` execute pre-push hooks by default. The
  explicit `--no-hooks` escape remains possible and is an accepted assumption,
  not a false guarantee.
- Husky is not added: this Deno project has no package manifest, and replacing
  `core.hooksPath` could bypass GitButler's managed hooks.
- Pre-deploy performs a read-only project/schema compatibility check. It never
  initializes metadata, claims a transition, or changes application data.
- Version `0` means only “no schema state exists.” It is not a wildcard matching
  an already-versioned database; wildcard matching would invalidate the write
  guard.
- A database-level manifest binds one database to a stable project ID. Once
  present, a different project fails before any schema write. The one-time
  version-0 bootstrap cannot infer identity from unversioned data, so its exact
  project/database URL is an explicit operator assertion.
- Manual writes require the official Deno KV connector URL, token environment,
  exact project ID, and complete explicit per-schema from/to vectors. The
  project and every from version must match durable metadata; every to version
  must match the code registry. Any mismatch performs no write.
- Existing forward-only, adjacent, idempotent helpers and Deno KV atomic claims
  remain the mutation mechanism after the guard passes.
- Revision preview URLs currently share one preview database while skipping
  pre-deploy. They are not a safe durable-schema acceptance environment. Git
  branch URLs have isolated databases and run pre-deploy; use those for
  database-dependent review.
- Deno Deploy currently builds/runs with Deno 2.5.0. Pin the project toolchain to
  that version and format with it; the observed CSS failure is formatter drift
  from local Deno 2.9.3.

## Required interfaces

- `DatabaseSchemaManifestRepository`: read and conditionally establish the
  stable project identity without exposing Deno types.
- `DatabaseSchemaVersionChecker`: read manifest and every declared schema,
  returning bounded `current`, `stale`, `future`, `pending`, `unversioned`, or
  `wrong_project` diagnostics without writes.
- `DatabaseSchemaWriter`: validate a complete project/from/to request before
  delegating to the existing forward upgrader.
- Deno KV implementations in an adapter-owned, versioned keyspace, with shared
  conformance tests and exact compare-and-set behavior.

## Commands

- Local hook: `deno task verify` (check and full tests).
- Deno Deploy pre-deploy: `deno task pre-deploy` (read-only schema check only).
- Manual remote mutation: one explicit task accepting database URL, project,
  complete from vector, and complete to vector; token comes only from
  `DENO_KV_ACCESS_TOKEN`.

## Verification

Cover hook installation and GitButler-compatible placement, task graph
separation, no-write checker behavior, wrong-project/stale/future/pending and
version-0 states, guarded bootstrap, exact vector mismatch with zero writes,
remote URL/argument/token validation, interrupted migration reuse, bounded
secret-free output, Deno 2.5 formatting/check/tests/build, and the read-only
pre-deploy command against in-memory adapters.

# Add conforming Kvdex page/content persistence

## Objective

Use pinned `jsr:@olli/kvdex@3.6.7` inside the durable page/content implementation
to store typed metadata and segmented PDF assets while preserving the stronger
application repository contracts already satisfied by memory and raw Deno KV.

This task covers page/content/endpoint persistence needed by the PDF slice. It
does not silently claim that identity, namespace, or session adapters have also
migrated to Kvdex; those repositories retain their own interfaces and require a
separate conformance-backed migration if later requested.

## Investigation already established

- Kvdex 3.6.7 supports Deno `^2.3.0`; this project currently runs Deno 2.9.3.
- Encoded collections segment `Uint8Array` into 64 KiB entries.
- A local 1 MiB probe fails as one Deno KV mutation with the native 819,200-byte
  limit and succeeds with Kvdex `{ batched: true }`, producing one ID record and
  seventeen segment records.
- Kvdex atomic builders explicitly reject encoded collections.
- Batched writes commit several atomic operations and are not one visibility
  transaction; a page must never reference such an asset while it is staging.
- Kvdex documents that built-in index deletion is not fully atomic.
- Existing application raw-KV records use a different keyspace and schema; the
  Kvdex migration helper does not transform them into the new domain model.

## Mandatory project invariants

1. Existing repository/content-asset/endpoint interfaces and their conformance
   define behavior. No Kvdex type may cross the adapter boundary.
2. Keep an in-memory reference and run the identical suite against Kvdex.
3. Do not weaken atomic locator uniqueness, revision checks, managed takeover,
   rename, duplicate, delete, owner ordering, or public exclusion for convenience.
4. Large content is staged immutably before visibility. A partially written,
   failed, or corrupt asset is never reachable from a page endpoint.
5. HTTP and UI remain absent. Storage does not choose PDF validity, delivery
   disposition, endpoint URLs, or authority.
6. Never switch the configured durable implementation in a way that makes the
   existing raw keyspace appear empty; compatibility/migration is acceptance work.
7. Pin the dependency in the import map/lock and synchronize README, specs,
   deployment/migration docs, CHANGELOG, tests, check, and build.

## Ordered plan

1. Design Kvdex schemas for immutable encoded assets and unencoded page,
   endpoint, owner-order, and public-order documents. Avoid built-in index paths
   that cannot satisfy atomic delete/write contracts.
2. Add an adapter-owned database/schema factory so repositories can share one
   supplied Deno KV instance without exposing Kvdex to composition callers.
3. Implement staged asset creation: write all segments, confirm reconstruction
   and metadata/hash/length, then publish only an unreferenced asset identity.
4. Atomically publish or change page and endpoint references through unencoded
   metadata collections. On failure, leave at most an unreachable asset and
   clean it best-effort; never expose mixed generations.
5. Implement reference-safe replacement, duplication, and deletion. Shared
   immutable assets must not be deleted while any page references them; define a
   bounded orphan cleanup/reconciliation path.
6. Preserve deterministic owner/public listing and cursor semantics without
   treating alternate endpoint aliases as pages.
7. Add corruption checks for missing, reordered, duplicate, oversized, or wrong
   asset segments and incoherent endpoint/page references.
8. Build explicit legacy compatibility: either a tested one-time raw-page to
   asset/page/endpoint migrator with verification and resumability, or a dual
   selection strategy that cannot silently hide records. Document rollback.
9. Run the complete old and new conformance, concurrency, multi-segment,
   interruption, migration, and shared-instance suites.
10. Only then select the Kvdex-backed page/content adapter for the durable
    backend and retire raw writes; run all tests, check, and build.

## Acceptance

- Memory and Kvdex pass the same page/content/endpoint conformance.
- Large PDFs round-trip byte-for-byte across repository instances.
- No endpoint resolves before every referenced segment is durable and verified.
- Concurrent create/takeover/rename/duplicate/update/delete operations preserve
  one complete winner and exact revisions.
- Alias and canonical endpoint indexes remain coherent after every operation.
- Failed batches create no visible page and cannot block future publication
  indefinitely.
- Existing raw Deno KV pages are discoverable after the documented migration or
  compatibility procedure; tests cover interruption and restart.
- Kvdex imports appear only in adapter/storage files.

## Not in this task

Identity, external-identity, namespace, or session repository migration; PDF
HTTP transport; site UI; generic binary storage API; external providers.
